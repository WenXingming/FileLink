# 存储可靠性与去重设计（MVP 历史说明）

> 本文只描述旧 `/upload` 小文件 MVP，不是可靠上传 V1 的最终方案。断点续传引入后，未完成暂存文件必须跨请求保留，不能再由单个请求对象的析构函数删除。可靠上传、状态机与掉电恢复请以 [可靠上传 V1 设计](可靠上传V1设计.md) 为准。

在 FileLink 项目的设计中，关于文件的**上传清理**、**并发去重**以及**离线存量去重**是三个完全独立且针对不同场景的机制。面试官往往会针对这几个场景考察你的架构边界设计能力。

## 1. 异常上传的自动清理：基于 RAII 的临时文件销毁
**问题场景**：用户在上传一个 2GB 文件时，传到 50% 突然断网。此时服务器磁盘上遗留了一个 1GB 的无用 `.tmp` 临时文件，久而久之会导致服务器磁盘爆满。
**解决方案**：通过 `StreamUploader` 的 **析构函数 (Destructor)** 配合 **RAII (Resource Acquisition Is Initialization)** 机制来解决。
- `StreamUploader` 对象在栈上创建。
- 只要上传未调用 `finalize()`（比如因为断网抛出异常退出了作用域），`isFinalized_` 就为 `false`。
- 当对象生命周期结束时，其析构函数会自动调用操作系统的 `::unlink(tempFilePath_.c_str())` 删除残缺文件。
- **适用边界**：这只适用于没有断点续传的单请求 MVP。析构清理不能替代过期会话扫描，也不能承诺进程被强杀或整机掉电后不存在残留。

## 2. 并发安全与秒传去重：基于 POSIX `link()` 的原子提交
**问题场景**：两个用户同时上传完全一样的文件，或者用户触发“秒传”。如果仅仅通过 `if (exists)` 判断，会存在严重的**并发条件竞争 (Race Condition)**。
**解决方案**：这部分功能是由底层的 `ObjectStore` 完成的，而不是 `StreamUploader`。
- 我们利用了 Linux 操作系统的原子语义：`link(tempPath, objectPath)`。
- 只有成功将临时文件硬链接为哈希名，才算成功。如果返回 `EEXIST` 错误，说明该哈希（对象）在并发瞬间已经被别人抢先落盘了。
- 此时复用现有对象并清理当前临时文件，实现并发去重。
- **准确表述**：`link()` 是正式名字的原子发布点，`EEXIST` 是并发仲裁结果；它不等于整个上传流程无锁，也不提供掉电持久性。掉电持久还需要同步文件内容和正式对象目录。

## 3. 掉电容灾与 CAS 语义完整性：基于 `fdatasync` 和 `fsync` 的提交协议
**问题场景**：数据写入临时文件后，往往还停留在操作系统内核的 Page Cache (内存) 中，并未真正落入物理硬盘。如果我们此时直接调用 `link()` 发布了正式文件名（如 `a1b2c3d4...`），而机器在下一秒突然断电。重启后，目录树中确实存在这个文件，但**文件内容却是一堆零或乱码**。
对于我们的 CAS (基于内容寻址) 系统来说，这是毁灭性的灾难：以后如果有用户上传真正的该文件，由于哈希相同，系统会报错 `EEXIST` 并触发“秒传”，导致所有用户永远只能下载到这个因断电而产生的乱码假文件。
**解决方案**：在 `ObjectStore::commit` 中引入严格的 **Write-Ahead, Publish-Atomically** 落盘协议：
1. **先落盘数据**：调用 `fdatasync(tempPath_fd)` 强制要求内核把文件数据刷入物理磁盘。
2. **后发布名称**：调用 `link(tempPath, objectPath)` 抢占正式命名空间（原子性）。
3. **固化目录树**：调用 `fsync(dir_fd)` 将包含新文件名的父目录结构元数据也刷入磁盘。
- **面试话术**：“为了保证基于哈希寻址（CAS）体系的绝对纯洁性，我处理了极端的宕机容灾场景（Crash Consistency）。如果单纯依赖操作系统的后台刷盘，断电会导致产生大小正确但内容损坏的‘空洞文件’，从而引发‘哈希占位毒化’。因此我在 `link` 暴露正式名字前，强制执行了 `fdatasync` 进行同步屏障，实现了存储引擎级别的 WAL (预写日志) 提交语义，保证落盘的文件哪怕断电也 100% 完整。”

## 4. 离线存量去重：专属的文件扫描 CLI 工具
**问题场景**：历史遗留系统中有大量的重复文件，需要在不影响线上 Web 服务的情况下把硬盘空间腾出来。
**解决方案**：这是由工程中独立的离线工具 `dedup CLI` 完成的。
- 采用双重遍历策略（先按文件大小分组，大小一样的再去并行计算 Blake3 哈希）。
- 发现相同哈希的文件，将其安全替换为硬链接（Hardlink）。
- **面试话术**：“对于存量数据的清理，由于它是一个重度 I/O 操作，我专门把它抽象为了一个离线分析工具。这体现了命令与查询分离的思路，绝不会让后台的离线清理任务阻塞核心的高并发 API 业务。”

## 5. 关于“孤儿对象回收 (Garbage Collection)”
目前纯后端的 FileLink 依靠哈希寻址（CAS）。可靠上传 V1 使用 MySQL 记录上传会话，后续也由 MySQL 记录 `用户 -> 逻辑文件 -> 物理对象` 的映射。
当用户在前端点击“删除文件”时，实际上只应该删掉数据库里的映射记录。
**回收机制**：需要写一个后台定时脚本，找出对象存储中**所有存在、但在数据库中没有映射记录的哈希**，然后将其安全删除。这就是真正的“孤儿回收”。

---
**总结提醒**：
千万不要混淆这四个概念：
1. **防垃圾文件** ➡️ `StreamUploader` (RAII 析构清理)
2. **防并发写冲突** ➡️ `ObjectStore` (`link` 原子性)
3. **防掉电数据损坏** ➡️ `ObjectStore` (`fdatasync` + `fsync` 持久化协议)
4. **存量盘点清理** ➡️ `dedup` (离线工具)
