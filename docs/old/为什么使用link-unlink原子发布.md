# 为什么使用 `link + unlink` 原子发布对象

## 1. 要解决的问题

FileLink 使用内容哈希作为物理对象的身份：

```text
storageRoot/
├── tmp/<upload-id>
└── objects/ab/cd/<blake3>
```

上传过程中，数据先写入临时文件。只有文件接收完整、BLAKE3 已确认后，它才可以出现在 `objects` 目录中。

提交过程需要满足三个约束：

1. 下载方不能看到只写了一部分的对象。
2. 多个相同内容的上传并发提交时，只保留一个物理对象。
3. 已存在的对象不能被后来的提交覆盖。

核心不变量是：

> `objects/<hash>` 不存在，或者已经指向一个完整且不可再修改的对象；不存在“半成品”状态。

## 2. 提交流程

简化后的流程如下：

```cpp
CommitResult commit(tempPath, objectPath) {
    // 前置条件：临时文件已经写完，写入句柄已经关闭。
    if (link(tempPath.c_str(), objectPath.c_str()) == 0) {
        unlink(tempPath.c_str());
        return Created;
    }

    if (errno == EEXIST) {
        unlink(tempPath.c_str());
        return Reused;
    }

    // 发布失败时保留临时文件，便于重试或排查。
    return Error;
}
```

这里真正承担“原子发布”职责的是 `link()`，`unlink()` 只是清理临时名字。不能把它表述成“两个系统调用组成了一个原子事务”。

## 3. `link()` 为什么可以作为发布点

`link(tempPath, objectPath)` 为同一个 inode 创建一个新的目录项：

```text
调用前：

tmp/upload-123 ──────> inode 42

调用成功后：

tmp/upload-123 ──────> inode 42
objects/ab/cd/hash ──> inode 42
```

这个操作具有两个关键语义：

- 新目录项要么完整创建成功，要么完全不存在，不会出现“半个文件名”。
- 如果 `objectPath` 已存在，`link()` 返回 `EEXIST`，不会覆盖它。

因此，`link()` 成功就是对象对读者可见的唯一线性化点。读者在它之前看不到对象，在它之后看到的一定是已经写完的临时文件所对应的 inode。

随后执行：

```text
unlink(tmp/upload-123)
```

只会删除临时目录项。此时 inode 仍被正式对象路径引用，链接计数从 2 变成 1，文件内容不会被删除，也不会发生数据复制。

## 4. 并发去重为什么不需要锁

假设请求 A 和 B 上传了相同内容，得到相同哈希，并同时提交：

```text
A: link(tmp/A, objects/hash) ──> 成功
B: link(tmp/B, objects/hash) ──> EEXIST
```

内核对同一个目标目录项进行仲裁：

- 只有一个请求能够创建 `objects/hash`。
- 获胜者返回 `Created`。
- 其他请求发现 `EEXIST`，返回 `Reused`。
- 所有请求都可以删除自己的临时文件。

这相当于利用文件系统完成一次原子的“存在则复用，不存在则创建”，不需要进程内互斥锁、分布式锁或数据库锁。

它还天然支持幂等：对同一哈希重复执行提交，最终始终只有一个正式对象。

## 5. 崩溃窗口

`link + unlink` 不是一个不可分割的整体。在不考虑机器掉电、仅讨论进程崩溃时，两个调用之间崩溃不会破坏正式对象。

| 崩溃时机 | 正式对象 | 临时文件 | 结果 |
|---|---|---|---|
| `link()` 之前 | 不存在 | 存在 | 可以重试或由后台清理 |
| `link()` 成功后、`unlink()` 前 | 完整存在 | 仍存在 | 两个路径指向同一 inode，仅遗留临时名字 |
| `unlink()` 之后 | 完整存在 | 不存在 | 正常完成 |

这种情况下最坏结果只是残留一个临时目录项，不会出现正式对象损坏或丢失。后台任务可以按创建时间清理过期临时文件。

## 6. 原子可见不等于掉电持久

`link()` 解决的是并发访问下的原子可见性，不自动承诺机器掉电后数据和目录项一定已经落盘。

如果系统需要严格的掉电恢复语义，完整流程还应包括：

1. 写完临时文件。
2. 对临时文件执行 `fsync()`，确保内容和必要元数据落盘。
3. 执行 `link()` 发布正式目录项。
4. 对正式对象所在目录执行 `fsync()`，确保新目录项落盘。
5. `unlink()` 临时目录项；如需严格保证清理结果，再同步临时目录。

简历或面试中应准确表述：

> `link()` 提供原子且不覆盖的命名空间发布；`fsync()` 负责掉电后的持久性。

## 7. 为什么不直接使用其他方案

### 7.1 先判断存在，再 `rename()`

```cpp
if (!exists(objectPath)) {
    rename(tempPath, objectPath);
}
```

`exists()` 与 `rename()` 之间存在 TOCTOU 竞态：多个线程都可能观察到目标不存在。

更重要的是，普通 `rename()` 在目标存在时会原子替换它。内容寻址存储中的对象应当不可变，后来者不应该替换已经发布的 inode。

### 7.2 直接写入正式路径

即使使用 `open(O_CREAT | O_EXCL)` 保证只有一个创建者，正式路径也会在写入完成前可见。读者可能观察到长度不断增长的半成品文件。

临时文件将“慢速写入”和“瞬间发布”分成了两个阶段。

### 7.3 使用锁文件或数据库锁

锁只能协调遵守同一协议的参与者，还需要处理锁超时、进程崩溃和遗留锁。这里的冲突对象本来就是一个文件系统目录项，直接使用内核提供的原子操作更简单。

### 7.4 `renameat2(RENAME_NOREPLACE)`

它同样可以实现“原子移动且不覆盖”，成功后临时路径会直接消失，是 Linux 上很好的替代方案。

选择 `link + unlink` 的主要理由是：

- `link()` / `unlink()` 属于更通用的 POSIX 接口。
- 不依赖 `renameat2()` 及文件系统对 `RENAME_NOREPLACE` 的支持。
- 发布成功与临时路径清理被明确分开，崩溃状态容易推理。

FileLink 本身面向 Linux，因此未来也可以评测并切换到 `renameat2(RENAME_NOREPLACE)`；二者需要维持相同的不覆盖语义。

## 8. 使用前提和限制

### 8.1 必须位于同一文件系统

硬链接不能跨文件系统，否则 `link()` 返回 `EXDEV`。因此上传临时文件应统一放在：

```text
storageRoot/tmp/
```

正式对象位于：

```text
storageRoot/objects/
```

二者天然处于同一个挂载点。外部批量导入的文件需要先进入本地 staging 区，再提交到对象库。

### 8.2 发布后必须保持不可变

硬链接的两个路径指向同一个 inode。如果仍有写文件描述符打开，发布后继续写入会直接修改正式对象。

因此提交接口必须要求：

- 文件已经写完并关闭写句柄。
- 哈希针对最终完整内容计算。
- 提交成功后不再通过任何文件描述符修改该 inode。

### 8.3 `EEXIST` 依赖内容哈希可信

发现正式路径已存在时，系统假设同一 BLAKE3 摘要代表同一内容。摘要必须由服务端根据实际上传数据计算，不能直接信任客户端传入的值。

对象损坏检测、定期校验和极端哈希冲突处理属于后续的数据完整性治理，不应混入最小提交路径。

### 8.4 不适用于所有远程文件系统

部分网络文件系统对硬链接、缓存一致性或故障返回值有额外限制。当前设计面向服务器本地文件系统；如果未来接入 S3 一类对象存储，应改用其条件写入能力，例如 “put if absent”。

## 9. 面试时可以怎样回答

简洁版本：

> 上传数据先写入同一文件系统中的临时文件，写完并计算 BLAKE3 后，通过 `link(temp, object)` 创建正式对象路径。`link` 对目录项的创建是原子的，而且目标已存在时返回 `EEXIST`、不会覆盖，因此并发上传相同内容时只有一个请求创建成功，其他请求直接复用。随后 `unlink(temp)` 只删除临时名字，不影响正式 inode。这里原子的是发布点，不是两个调用组成的事务；如果要求掉电持久，还要对文件和目录执行 `fsync`。

面试官继续追问时，可以展开三个点：

1. 为什么不用普通 `rename()`：它默认会覆盖已有目标，破坏不可变对象语义。
2. 崩溃是否安全：`link` 后、`unlink` 前崩溃只会遗留临时硬链接，正式对象仍完整。
3. 有什么限制：必须同一文件系统，发布前必须关闭写句柄，`fsync` 才负责掉电持久性。
