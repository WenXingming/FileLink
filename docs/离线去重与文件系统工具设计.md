# 离线去重与文件系统工具 (dedup) 设计方案

本篇文档记录了 FileLink 中离线文件去重工具 `dedup` (基于 [dedup_lib](file:///home/wxm/FileLink/CMakeLists.txt#L24) 库构建) 的设计定位，并系统性地阐述了**为什么将其放入系统 Cron 定时任务进行异步调度**的架构级论点，作为系统高可用存储和降本增效的核心技术说明。

---

## 1. 业务背景与定位

在 FileLink 系统中，虽然我们已经在在线分片上传路径（[ObjectStore::commit](file:///home/wxm/FileLink/src/ObjectStore.cpp#L112)）中实现了哈希排重与秒传机制，但我们依然设计并构建了一个离线去重命令行工具 `dedup`，并将其配置为**系统 Cron 定时任务**定期执行。

**核心定位**：
* **在线去重 (Inline Deduplication)**：解决的是通过标准 Web API 上传时的流量与存储空间节省问题（强一致性、秒级响应）。
* **离线去重 (Offline / Post-process Deduplication)**：作为底盘的保底机制，解决非在线 API 渠道导入、历史遗留、运维失误以及磁盘静默损毁导致的数据不一致与物理存储浪费问题（弱一致性、低优先级、大数据量）。

---

## 2. 为什么需要将 `dedup` 放入定时任务？(说服面试官的硬核理由)

面试官通常会质疑：“在线上传已经有去重和秒传了，为什么还要在后台跑一个定时扫描去重工具？这难道不是多此一举吗？”

我们可以通过以下三个具有深度工程洞察的架构级理由进行解答：

### 理由 1：容错非在线渠道写入的“存储黑洞”（孤儿与重复文件治理）
在真实的生产环境中，存储挂载点（`/data/filelink/storage`）并非 100% 仅由 Web 进程独占和写入。系统管理员或运维工具往往会绕过 API 接口，直接对底层文件系统进行操作：
1. **运维直接导入**：使用 `rsync` 快速同步、FTP 传输、或通过 Samba 共享直接导入几十 GB 的模型权重和数据集文件。
2. **孤儿文件产生**：在系统升级、网络灾备同步、或者手动维护失误时，可能在存储目录下残留未登记在 MySQL 中的重复物理文件，或是被放弃上传的 `.part` 临时文件。
* **必要性**：这些“黑渠道”导入或残留的文件，**完全绕过了在线 API 的去重和校验逻辑**，会瞬间吞噬磁盘。通过 Cron 定时运行 `dedup` 深度扫描，能够将这些非 API 写入的重复内容在底层文件系统层面**原子替换为硬链接 (Hard Link)**，实现静默空间回收，避免存储失控。

### 理由 2：极致的“延迟去重 (Deferred Deduplication)”以换取高峰期吞吐量
在超高并发或极端吞吐量的业务场景下，实时计算哈希并进行在线去重的开销是无法承受的：
1. **CPU/IO 密集开销**：对 100GB 的文件进行完整的 Hash 计算和原子 link，即使使用了流式哈希，也会占用大量的 CPU 时间片并产生磁盘读写竞争，造成在线 API 的响应延迟（P99 飙升）。
2. **架构退避（延迟去重）**：
   * 在高峰期，API 允许先快速写入文件并返回，只做元数据记录（退避强哈希计算）。
   * 在凌晨 3:00 等系统低峰期，通过 Cron 任务触发离线去重工具 `dedup`。它会多线程遍历新文件、异步计算哈希、并在文件系统底层通过硬链接合并相同的内容。
   * 这种“先写入、后异步去重”的机制（在大型存储系统如 Dropbox, Borg 中广泛应用）能够让 FileLink 在高峰期保持极致的写入吞吐能力。

### 理由 3：主动防御：数据完整性审计 (Integrity Auditing) 与自愈 (Self-healing)
将 `dedup` 定时任务跑在后台，实际上它也承担了 FileLink 的**“底盘一致性审计与健康巡检引擎”**职责：
1. **防止数据静默损坏 (Bit Rot)**：由于硬件老化或磁盘磁道损坏，文件数据可能在未被察觉的情况下发生变异，导致其实际哈希与 MySQL 中的记录不符。
2. **审计与报警**：定时全盘扫描会在低峰期重新校验所有文件的 Hash 值，一旦发现现有文件的 Hash 与注册的不匹配，立即触发审计日志和系统报警。
3. **数据自愈**：如果检测到同一个文件的副本发生了部分损坏，而另一个完全相同的副本哈希正确，离线去重工具能够通过重建硬链接自动用好的文件副本覆盖掉坏的副本，实现存储层的数据自愈。

## 3. 定时任务配置与运行机制

基于以上理由，我们将 `dedup` 命令行工具的执行逻辑进行了轻量级且无感的设计：

### 3.1 运行指令设计
因为我们采用“机制与策略分离”的方案，将去重逻辑以子命令形式集成到了主程序 `filelink-server` 中，因此在服务器的 Cron 定时中进行如下配置：
```bash
# 每天凌晨 4:00 执行重复文件扫描与去重合并，并仅在磁盘 I/O 空闲时运行
0 4 * * * ionice -c 3 /usr/local/bin/filelink-server --storage-root /data/filelink/storage --dedup >> /var/log/filelink_dedup.log 2>&1
```

### 3.2 扫描去重算法 (dedup_lib) 的实现路径
通过 `dedup_lib` 扫描时，为保证极低的系统资源占用，算法做了如下防抖和性能优化：
1. **分级快速过滤 (Size-based Pre-filtering)**：
   * 第一步只读取目录树下所有文件的大小（`stat`）。
   * 排除大小唯一的文件（不可能有重复），只对大小完全一致的文件组进行后续处理。
2. **分段哈希比对 (Segmented Hashing)**：
   * 对于相同大小的大文件，先只读取其头部 4KB 和尾部 4KB 计算部分哈希比对。
   * 只有当头尾哈希也完全一致时，才启动全文件 BLAKE3 扫描，避免盲目对所有大文件做全盘 I/O 读写。
3. **原子硬链接替换 (Atomic Replacement)**：
    * 确认哈希一致后，利用临时文件硬链接 + `rename` 操作进行原子替换，确保去重过程中即使系统遭遇断电，也不会导致任何原始文件丢失。

### 3.3 本地项目集成：DedupRunner 与原子物理落盘

主项目利用 `DedupRunner` 承载去重的具体落地过程：
1. **轻量级单实例多线程扫描**：
   * 在 [DedupRunner.cpp](file:///home/wxm/FileLink/src/cleaner/DedupRunner.cpp) 中，我们限制去重扫描的线程池大小为 2（并发数量低，保障 I/O 调度不把系统总线占满），调用底层 `DuplicateFinder` 针对 `${storageRoot}/objects` 进行递归碰撞扫描。
2. **原子硬链接替换机制 (Atomic Hardlink Swap)**：
   扫描得到 `DuplicateGroup` 后，对组内每个冗余文件（targetPath）的去重替换在文件系统级别做到了**完全原子性**：
   * 首先，调用 `::link(anchorPath.c_str(), tempPath.c_str())` 在相同设备上为源锚点文件生成一个临时硬链接名（如 `${targetPath}.tmp_dedup`）。
   * 接着，调用 `::rename(tempPath.c_str(), targetPath.c_str())` 原子地用该链接覆盖原重复文件。
   * **安全性保证**：由于 `rename` 是 POSIX 标准的文件系统级原子调用，在任何时刻发生断电或崩溃，用户都绝对不会丢失原始文件路径的访问权限，也不会产生数据错乱，保障了线上自愈的高可用性。
