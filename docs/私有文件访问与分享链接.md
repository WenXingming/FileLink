# 私有文件访问与分享链接

FileLink 的 Object 可以被多个 File 引用，但 Object 从不直接对外暴露。**权限判断永远先落在 File：私有访问看 File 的所有者，公开访问看 File 的有效 Share。**

因此，内容去重不会变成越权访问：Alice 和 Bob 即使引用同一个 Object，也各自只拥有自己的 File。

## 两条下载链路

```text
私有下载
Cookie → 当前 User → file_id + owner_user_id → File → Object → 文件响应

公开分享下载
URL 原始 token → BLAKE2b(token) → 有效 Share → File → Object → 文件响应
```

两条路径最后都会生成 Object 的内部对象键，但前面的授权条件完全不同。系统没有 `GET /objects/<content_hash>` 这样的公开接口，客户端不能凭内容哈希绕过 File 的归属关系。

## 私有文件：以所有权作为唯一入口

私有文件接口都要求登录 Cookie：

| 接口 | 行为 |
| --- | --- |
| `GET /files` | 列出当前用户的逻辑文件，按创建时间倒序 |
| `GET /files/<fileId>/download` | 下载当前用户拥有的文件 |
| `DELETE /files/<fileId>` | 删除当前用户拥有的逻辑文件 |

`RequestAuthenticator` 先将 Cookie 解析为当前 `user_id`。随后 `FileService` 使用 `FileDao::find_by_id_and_owner(file_id, owner_user_id)` 查询，而不是先按 `file_id` 查到 File 后再比较所有者。

```sql
SELECT ... FROM files
WHERE file_id = :file_id AND owner_user_id = :owner_user_id
```

这有两个效果：

1. 权限条件靠近数据查询，调用者无法忘记做所有权校验。
2. 不属于当前用户和根本不存在都返回 `404 Not Found`，避免攻击者枚举 File ID 后确认某个文件存在。

### 为什么 File 而不是 Object 承载权限

假设 Alice 与 Bob 都上传了内容哈希为 `H` 的相同 PDF：

```text
File(Alice, "简历.pdf") ─┐
                         ├─► Object(H)
File(Bob,   "备份.pdf") ─┘
```

Object 只表示不可变字节，不知道文件名和用户。若下载接口只接受 `H`，Bob、Alice 和猜到 H 的任何人都会处于同一权限层级，私有文件库就失去意义。以 File 为授权对象后，Alice 的 Cookie 只能匹配 Alice 的 File，不能下载 Bob 的 `备份.pdf`。

## 下载为何交给 Nginx

授权成功后，`FileApiRouter` 或 `ShareApiRouter` 将 File 的二进制 `content_hash` 转成内部对象键，并返回空响应体及以下响应头：

```text
Content-Type: application/octet-stream
Content-Disposition: attachment; filename="<安全文件名>"
X-Accel-Redirect: /_filelink_objects/<对象键>
```

Nginx 收到 `X-Accel-Redirect` 后，通过受 `internal` 保护的路径映射只读对象目录并发送正文。FileLink 不打开或读取对象文件，应用进程内存不会随下载大小增长；官方 Nginx 镜像的主配置启用了 `sendfile on`。完整的数据路径和内存边界见[大文件上传与下载数据路径](大文件上传与下载数据路径.md)。

展示文件名来自 `files.display_name`，下载响应会将不可打印字符、双引号和反斜杠替换为 `_`，避免它们破坏 `Content-Disposition` 响应头。

## 分享：给一个 File 增加临时公开授权

分享管理接口仍需要文件所有者登录：

| 接口 | 行为 |
| --- | --- |
| `POST /files/<fileId>/shares` | 创建分享，Body 为 `{"expires_in_seconds": ...}` |
| `GET /files/<fileId>/shares` | 列出当前仍有效的分享 |
| `DELETE /files/<fileId>/shares/<shareId>` | 撤销一条分享 |
| `GET /shares/<token>/download` | 不需要 Cookie 的公开下载 |

创建时先按 `file_id + owner_user_id` 确认 File 属于当前用户，过期时间必须大于当前时间且不超过 30 天。服务生成 32 字节随机 token 和独立的 `share_id`：

```text
客户端只获得一次：原始 token 的 64 位十六进制文本
MySQL shares 表保存：BLAKE2b(token)、file_id、expires_at、revoked_at
```

原始 token 不会在“分享列表”接口中重新返回。用户若复制后丢失它，应创建新的分享；这是避免数据库、日志或后续 API 响应意外泄露可用链接的边界。

### 公开下载时检查什么

`GET /shares/<token>/download` 不读取 Cookie。它将 URL 中 token 解码并计算 BLAKE2b 哈希，再查询：

```sql
SELECT ... FROM shares
WHERE token_hash = :token_hash
  AND revoked_at IS NULL
  AND expires_at > NOW(6)
```

命中后才读取关联的 File，并复用同一套文件响应逻辑下载 Object。错误 token、已撤销、已过期、关联 File 不存在或物理对象缺失，对外都返回 `404`；公开请求不需要知道失败的具体原因。

Share 授权的是 File，而不是 Object，因此它自然带有该 File 的展示名和生命周期。删除 File 时，外键 `ON DELETE CASCADE` 删除所有 Share；撤销只写入 `revoked_at`，保留记录用于审计式排查，但不再能被有效查询命中。

## 路由委托：为什么分享管理不直接注册 `/files/` 路由

Tudou 的前缀路由按注册顺序独占匹配。`/files/<id>/download`、`/files/<id>` 与 `/files/<id>/shares` 都以 `/files/` 开头；如果 `FileApiRouter` 和 `ShareApiRouter` 分别注册同一前缀，先注册的一方会吞掉另一方的请求。

实际结构是：

```text
FileApiRouter 注册唯一的 /files/ 前缀
     │
     ├─ 先询问 ShareApiRouter：是否是 /files/<id>/shares... 管理请求？
     │      └─ 是：由 ShareApiRouter 处理
     │
     └─ 否：处理私有下载或删除

ShareApiRouter 独立注册 /shares/ 前缀
     └─ 处理不需要登录的公开下载
```

这不是让文件模块承担分享业务，而是对 Tudou 路由规则做的一层很薄的 HTTP 分发适配。实际分享规则仍在 `ShareService` 中。

## 用一个例子验证权限模型

1. Alice 上传 `report.pdf`，得到 `File(A, Alice, H)`；Bob 上传相同内容，得到 `File(B, Bob, H)`。两者指向同一 Object `H`。
2. Alice 用 Cookie 请求 `GET /files/B/download`。查询条件包含 `owner_user_id = Alice`，没有匹配行，返回 `404`。
3. Alice 为 A 创建七天分享，浏览器只在创建响应中拿到 token `T`。
4. 未登录访问者请求 `/shares/T/download`，服务以 `BLAKE2b(T)` 找到有效 Share，再下载 A 对应的 Object。
5. Alice 撤销分享或删除 A。之后使用 T 的公开请求都返回 `404`；Bob 的 File B 和对 H 的引用不受影响。

这个例子体现了三件事：物理去重不等于共享权限；分享是可撤销的 File 授权；删除一个逻辑 File 不会伤害仍引用同一 Object 的其他用户。

## 面试时的讲述重点

“我没有给内容哈希设计公开下载接口，而是把权限放在逻辑 File 上。私有访问将 Cookie 解析出的 user_id 与 file_id 一起查询，非所有者统一返回 404；这样相同 Object 被多用户去重引用时也不会串权限。分享是独立的、可过期和可撤销的 File 授权，数据库只存随机 token 的 BLAKE2b 哈希，创建时原始 token 仅返回一次。两种下载都由 FileLink 完成授权并返回 X-Accel-Redirect，再由 Nginx 从只读对象目录发送文件，避免将大对象读入应用内存。”
