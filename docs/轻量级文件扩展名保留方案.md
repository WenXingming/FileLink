# 轻量级文件扩展名保留方案 (无数据库实现)

在内容寻址存储（Content-Addressable Storage）系统中，文件物理落盘时完全依赖文件内容的 Hash 值（如 BLAKE3）作为文件名。这就产生了一个体验上的问题：用户上传了 `photo.jpg`，下载时浏览器往往无法识别其文件类型，导致保存成了一个无后缀的哈希字符串文件。

传统解法是引入关系型数据库（如 SQLite），建立 `Hash -> Original Filename` 的映射，这使得架构变得沉重。
为了在 MVP（最小可行性产品）阶段保持架构极简，同时完美解决扩展名丢失和浏览器无法预览的问题，我们采用了一种巧妙的**URL 扩展名透传设计**。

## 核心设计思路

### 1. 上传阶段：截取后缀并融入分享 URL
前端在发起上传请求时，通常会通过 `X-File-Name` 请求头传递原始文件名（例如 `X-File-Name: photo.jpg`）。
服务端的 `ApiRouter::handleUpload` 不再将原文件名持久化，而是仅仅**提取其扩展名**（`.jpg`）。在构建返回给前端的成功响应时，直接把扩展名拼接到生成的 URL 尾部：

```json
// 返回给前端的响应体
{
    "status": "success",
    "hash": "d74981efa7...",
    "result": "created",
    "url": "http://127.0.0.1:8080/objects/d74981efa7....jpg"
}
```

### 2. 下载阶段：动态剥离后缀并推理 MIME
当用户点击链接或在浏览器地址栏访问 `http://127.0.0.1:8080/objects/d74981efa7....jpg` 时，请求将打到服务端的 `ApiRouter::handleDownload`。

服务端进行两步轻量化处理：
1. **剥离后缀寻找真实数据**：
   从请求路径中找到最后一个 `.`，拆分出 Hash 部分（`d74981efa7...`）和扩展名部分（`.jpg`）。然后用纯净的 Hash 去底层的 `LocalObjectStore` 中查找到真实的无后缀物理文件，读取其内容。
2. **基于后缀设置 MIME 类型**：
   利用提取出的扩展名，进行简单的 MIME 推断（如 `.jpg` 映射为 `image/jpeg`）。然后将该 MIME 类型塞入 `Content-Type` 响应头。

## 方案的优势

1. **绝对的零依赖（Zero DB）**：整个生命周期没有用到任何额外的存储开销去记录状态，完全契合网盘基座轻量、无状态的理念。
2. **浏览器原生友好**：
   - 因为 URL 本身就是以 `.jpg` 结尾，所以当用户在浏览器按下“另存为”时，浏览器会自动填充文件名为 `[Hash].jpg`，完美保留了后缀。
   - 因为我们在 HTTP Header 返回了准确的 `Content-Type: image/jpeg`，浏览器不再将其视作 `application/octet-stream` 强制下载，而是能够在浏览器内直接预览图片、播放视频或渲染文本。

## 未来演进 (B 路线)
此方案是 MVP 阶段的“神来之笔”，能够快速提供 90% 的良好体验。
但当业务发展，要求实现“文件夹结构展示”、“原文件名完全还原”、“多文件重名区分”等完整网盘能力时，依然需要走向标准的架构：引入 SQLite 数据库记录完整的元数据信息。
