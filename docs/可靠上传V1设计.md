# FileLink 可靠上传 V1 设计

## 1. 文档目的

当前 FileLink 已经跑通：

```text
POST /upload
→ Tudou 收完整 HTTP Body
→ StreamUploader 写临时文件并计算 BLAKE3
→ ObjectStore 原子发布
→ GET /objects/{hash} 下载
```

这证明了内容寻址存储的最小闭环，但它仍然是“小文件 MVP”，还不能支撑“数 GB 到数十 GB 大文件可靠分发”的项目定位：

- Tudou 会先把完整请求体放入 `std::string`，内存占用与文件大小线性相关。
- 一个长连接中断后，整个文件需要重新上传。
- 没有上传会话、服务端 offset、幂等重试和进程重启恢复。
- 下载仍会把整个文件读入内存。
- 当前 `flush + close + link` 只保证进程运行期间的原子可见性，没有定义掉电持久性。

可靠上传 V1 的目标不是增加更多技术名词，而是建立一条状态正确、可恢复、可测试的上传链路。

## 2. 设计边界

### 2.1 V1 必须实现

- 单机、单服务进程。
- 固定总长度的顺序 offset 上传。
- 每个请求只携带一个有大小上限的数据块。
- 创建会话、查询 offset、追加数据、完成上传。
- offset 不匹配时拒绝写入，重复请求不产生重复数据。
- PATCH 成功返回的 offset 在进程崩溃和整机掉电后都能够恢复。
- 服务端计算最终 BLAKE3，不信任客户端摘要。
- 完成上传后，物理对象具备明确的掉电持久性边界。
- 未完成会话能够过期并被清理。

### 2.2 V1 明确不做

- 多机上传和分布式锁。
- 并行、乱序分片。
- 完整兼容 tus 协议。
- S3 Multipart Upload。
- 消息队列、微服务和 DI 容器。
- 让 Redis 参与上传 offset、状态机或文件发布的正确性链路。
- 在本阶段同时实现用户、分享链接和文件夹。

顺序 offset 是有意选择，不是能力缺失：

- 不需要分片合并。
- 正常情况下可以持续增量计算 BLAKE3，避免完成后再读一遍整个文件。
- 单个暂存文件只做顺序写，磁盘访问模式简单。
- 状态只有一个单调递增 offset，幂等和恢复更容易证明。

如果后续性能测试证明单流上传不能利用网络或磁盘，再增加并行分片；不能仅因为其他项目写了“并行分片”就提前承担复杂度。

## 3. 核心不变量

实现和测试都应围绕不变量，而不是围绕类名。

### 3.1 会话不变量

```text
0 <= committed_offset <= total_size
```

- `committed_offset` 表示已经向客户端确认、且对应文件数据已经持久化的边界。
- `committed_offset` 只允许单调递增，正常恢复时不回退。
- 只有 `UPLOADING` 状态允许接收数据。
- 请求 offset 必须与当前 `committed_offset` 完全相等。
- `COMPLETED` 状态必须保存服务端计算的 `content_hash`。
- `COMPLETED` 状态对应的物理对象必须先于 MySQL 记录完成持久化。

### 3.2 文件不变量

```text
数据库 committed_offset
<= 暂存文件当前长度
```

进程可能在“文件已写入、offset 尚未提交”之间崩溃，所以暂存文件允许比数据库 offset 更长。恢复时必须：

```text
truncate(temp_file, committed_offset)
```

然后才允许继续上传。

按照“先 `fdatasync` 文件、再提交 MySQL offset”的写入顺序，正常的进程崩溃或整机掉电不应出现暂存文件短于数据库 offset。若恢复时仍观察到这种情况，说明磁盘、文件系统或程序不变量已被破坏，不能静默回退；应将会话标记为 `FAILED` 并记录错误，避免把未知数据当成可靠前缀。

### 3.3 部署假设

- 暂存目录和对象目录位于同一个本地 POSIX 文件系统，保证 `link()` 不会因跨文件系统返回 `EXDEV`。
- V1 的耐久语义面向 Linux 上常见的 ext4/XFS，不把 NFS、FUSE 或具有特殊缓存语义的存储视为等价环境。
- 存储设备必须正确实现 flush/barrier；软件无法弥补虚假报告落盘的硬件。
- 正式对象只读且不可原地修改。对象损坏由后续 scrub 工具发现和隔离，不允许覆盖修复。

### 3.4 对象不变量

```text
objects/<hash>
```

只能处于两种状态：

- 不存在。
- 指向一个完整、已验证且不再修改的对象。

不存在正式路径可见但内容仍在增长的中间状态。

## 4. 为什么选择 offset 协议

本设计借鉴 tus 核心协议的 offset 语义，但只实现 FileLink 自己需要的子集，不在响应中宣称 `Tus-Resumable`，也不声称兼容 tus 客户端。

### 4.1 创建会话

```http
POST /uploads
Upload-Length: 10737418240
X-File-Name: model.bin
X-Content-Hash: <optional client blake3>
Content-Length: 0
```

成功：

```http
HTTP/1.1 201 Created
Location: /uploads/<upload-id>
Upload-Offset: 0
Upload-Length: 10737418240
```

约束：

- `Upload-Length` 必填且不能超过服务端最大文件大小。
- 文件名只作为展示元数据，不参与服务端路径拼接。
- 客户端 Hash 可用于最终完整性比对和未来秒传预检，但不能作为服务端对象身份的唯一依据。
- 暂存文件固定为 `storageRoot/uploads/<upload-id>.part`。
- `upload-id` 由服务端生成，使用不可预测的 128 位随机值。

### 4.2 查询进度

```http
HEAD /uploads/<upload-id>
```

成功：

```http
HTTP/1.1 200 OK
Upload-Offset: 8388608
Upload-Length: 10737418240
Upload-State: uploading
Cache-Control: no-store
```

客户端在以下场景必须先查询 offset：

- 进程重启。
- 网络中断。
- PATCH 响应丢失。
- 收到 `409 Conflict`。

### 4.3 追加数据

```http
PATCH /uploads/<upload-id>
Upload-Offset: 8388608
Content-Type: application/offset+octet-stream
Content-Length: 8388608

<binary chunk>
```

成功：

```http
HTTP/1.1 204 No Content
Upload-Offset: 16777216
```

规则：

1. `Content-Length` 必须存在。
2. 请求体不能超过 `maxChunkBytes`。
3. 请求 offset 等于服务端 offset 时才允许写入。
4. 请求 offset 小于或大于服务端 offset 时返回 `409 Conflict`，并携带当前 offset。
5. offset 不匹配时不能修改暂存文件和数据库。
6. `offset + Content-Length` 不能超过 `total_size`。

这满足幂等语义：

```text
服务器已写入 chunk
→ 响应在网络中丢失
→ 客户端使用旧 offset 重试
→ 服务端返回 409 和新 offset
→ 文件不会重复追加
→ 客户端 HEAD 后继续
```

### 4.4 完成上传

```http
POST /uploads/<upload-id>/complete
Content-Length: 0
```

前置条件：

```text
committed_offset == total_size
```

成功返回服务端计算的 BLAKE3、对象状态 `created/reused` 和逻辑下载地址。重复调用 complete 必须返回相同结果，不重复发布对象。

### 4.5 终止与过期

V1 后半阶段增加：

```http
DELETE /uploads/<upload-id>
```

未完成上传具有 `expires_at`。后台清理流程只能删除：

- 状态为 `UPLOADING`、`FAILED` 或 `ABORTED`；
- 已超过过期时间；
- 当前没有活跃写入者；
- 暂存路径确实位于 `storageRoot/uploads`。

## 5. 请求体内存上限

仅规定客户端“请发送小 chunk”并不能保护服务器。恶意或错误客户端仍然可以发送数 GB 请求体，而当前 Tudou 会在业务 Handler 执行前完整缓冲它。

因此，可靠上传接口上线前，Tudou 必须支持服务端请求体上限：

```text
on_headers_complete
→ 检查 Content-Length
→ 超过 maxRequestBodyBytes 立即返回 413
```

如果未来支持 `Transfer-Encoding: chunked`，还必须在每次 `on_body` 时累计长度，超过上限立即停止解析。V1 可以直接要求 `Content-Length`，拒绝未知长度的 PATCH。

有界请求体之后，内存模型从：

```text
O(文件大小)
```

变为：

```text
O(并发 PATCH 数 × maxChunkBytes)
```

注意：这仍然是“有界缓冲”，不是端到端流式。后续 Tudou streaming route 可以继续把单个 chunk 的内存占用降为网络缓冲区大小。

## 6. 上传状态机

```text
                  complete
UPLOADING ─────────────────────> FINALIZING
    │                                  │
    │ abort / expire                   │ durable object + DB commit
    v                                  v
ABORTED / EXPIRED / FAILED         COMPLETED
```

状态含义：

| 状态 | 是否可 PATCH | 是否可 complete | 说明 |
|---|---:|---:|---|
| `UPLOADING` | 是 | offset 满时可以 | 正常接收数据 |
| `FINALIZING` | 否 | 重试触发恢复 | 正在校验或发布对象 |
| `COMPLETED` | 否 | 幂等返回原结果 | 物理对象和完成记录均已持久化 |
| `FAILED` | 否 | 否 | 最终 Hash 不匹配或不可恢复错误 |
| `ABORTED` | 否 | 否 | 用户主动终止 |
| `EXPIRED` | 否 | 否 | 超时回收 |

不要为每个临时错误增加状态。磁盘瞬时错误、MySQL 连接失败或锁等待超时等应让本次请求失败，但会话仍保持 `UPLOADING`，允许客户端重试。

## 7. MySQL 数据模型

V1 只建立一张上传会话表：

```sql
CREATE TABLE upload_sessions (
    upload_id         BINARY(16) PRIMARY KEY,
    state             VARCHAR(16) NOT NULL,
    file_name         VARCHAR(255) NOT NULL,
    total_size        BIGINT UNSIGNED NOT NULL,
    committed_offset  BIGINT UNSIGNED NOT NULL DEFAULT 0,
    expected_hash     BINARY(32) NULL,
    content_hash      BINARY(32) NULL,
    failure_reason    VARCHAR(255) NULL,
    created_at        DATETIME(6) NOT NULL,
    updated_at        DATETIME(6) NOT NULL,
    expires_at        DATETIME(6) NOT NULL,
    CONSTRAINT chk_upload_offset
        CHECK (committed_offset <= total_size),
    CONSTRAINT chk_upload_state
        CHECK (state IN (
            'UPLOADING', 'FINALIZING', 'COMPLETED',
            'FAILED', 'ABORTED', 'EXPIRED'
        )),
    INDEX idx_upload_expiry (state, expires_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`upload_id` 对外使用不可预测的 128 位随机 token，对内存为 `BINARY(16)`；BLAKE3 使用固定的 `BINARY(32)`，避免用十六进制字符串浪费索引和行空间。暂存路径由 `storageRoot + upload_id` 推导，不接受数据库或客户端提供任意路径，减少路径穿越和误删风险。

MySQL 约束：

- 使用 InnoDB，不使用 MyISAM。
- 使用预处理语句，不拼接 SQL。
- `innodb_flush_log_at_trx_commit=1`；若启用 binlog 并要求复制链路同等耐久，使用 `sync_binlog=1`。
- 文件 I/O、BLAKE3 和 `fdatasync` 不能放在数据库事务内。
- 状态更新尽量使用单条条件 `UPDATE`，检查 affected rows，不先读后写。

选择 MySQL 的理由：

- FileLink 后续还需要用户、逻辑文件、分享链接、权限和审计等关系数据，MySQL 可以承载完整业务闭环。
- InnoDB 事务、行锁、唯一约束和条件更新能够表达状态机与幂等。
- 独立数据库服务更贴近团队应用的部署形态，也便于展示连接池、索引、事务和慢查询治理。
- 代价是增加部署、连接管理和故障边界，因此不能把一个本地文件写入包装成“跨 MySQL 与文件系统的原子事务”。

V1 使用一个具体的 `UploadSessionStore` 和小型连接池，不提前建立仓储接口、工厂层级或 DI 容器。数据库测试通过独立 MySQL 测试实例、migration 和测试数据清理隔离；不为了 fake 数据库提前抽象第二套实现。

### 7.1 Redis 的边界

V1 不需要 Redis。上传 offset、状态、Hash 和完成结果必须以 MySQL 为唯一事实来源，HEAD 也直接查询 MySQL，避免缓存旧 offset 破坏协议。

后续出现真实需求时再引入 Redis：

- 登录会话或 token 撤销；
- 接口限流；
- 热门分享链接元数据的 cache-aside 缓存；
- 短期幂等 token。

即使引入，缓存 miss 或 Redis 故障也只能影响性能和限流降级，不能使已上传文件丢失或状态回退。下载次数上限、对象引用计数等强一致数据仍由 MySQL 条件更新决定。

## 8. 会话创建与 chunk 崩溃恢复

### 8.1 会话创建顺序

创建会话同样存在文件系统和 MySQL 两个持久化边界，顺序为：

```text
1. 生成 upload-id
2. 以 O_CREAT | O_EXCL 创建 uploads/<id>.part
3. fdatasync(temp_fd)
4. fsync(uploads_dir_fd)
5. 向 MySQL 插入 UPLOADING 会话
6. 返回 201
```

选择“先文件、后数据库”是因为中途崩溃最多留下一个可扫描清理的零字节孤儿暂存文件；如果先提交数据库，则可能产生指向不存在暂存文件的坏会话。MySQL 插入失败时尽力删除临时文件，启动扫描负责兜底清理。

### 8.2 chunk 写入顺序

同一 upload-id 的请求必须通过会话级互斥串行化。MySQL 条件更新可以防止状态误更新，但不能单独阻止两个线程同时修改同一个暂存文件。

一次 PATCH 的顺序：

```text
1. 获取 session mutex
2. 从 MySQL 读取会话
3. 校验 state、offset、长度
4. 检查并修复 temp file 长度
5. 使用 pwrite 从 committed_offset 写入完整 chunk
6. fdatasync(temp_fd)
7. MySQL 条件 UPDATE 提交 committed_offset
8. 返回新 offset
```

这里不能交换第 6、7 步：只有文件数据已经持久化，数据库才能把新 offset 变成可向客户端确认的事实。MySQL/InnoDB 使用 `innodb_flush_log_at_trx_commit=1`，使成功提交的 offset 事务达到相应的掉电持久性边界。

`pwrite` 必须循环处理短写和 `EINTR`。任一步失败都不能推进 offset；如果 Hasher 已吸收或文件已写入未提交字节，则截断回旧 offset，并在下次请求前重建 Hash 状态。

CAS 形式：

```sql
UPDATE upload_sessions
SET committed_offset = :new_offset,
    updated_at = :now
WHERE upload_id = :id
  AND state = 'UPLOADING'
  AND committed_offset = :old_offset;
```

受影响行数必须为 1，否则本次请求视为冲突，不能继续假设自己持有最新状态。

如果执行条件 `UPDATE` 时连接中断，应用可能无法判断 MySQL 是否已经提交。此时不能立刻把文件截断到旧 offset，也不能直接返回成功，而应在连接恢复后重新查询：

```text
数据库 offset == new_offset → 事务已提交，按新 offset 继续
数据库 offset == old_offset → 事务未提交，截断未提交尾部
其他 offset                 → 发生并发推进，返回 409 和当前 offset
数据库仍不可用              → 返回 503，保留文件现场等待恢复
```

状态迁移同样遵循这一规则。条件更新和幂等 complete 使“提交结果未知”可以通过重新读取状态收敛，而不需要猜测。

### 8.3 崩溃矩阵

| 崩溃点 | 文件 | MySQL | 恢复动作 |
|---|---|---|---|
| 写入前 | 旧长度 | 旧 offset | 直接重试 |
| chunk 写到一半，`fdatasync` 前 | 可能比 offset 多一段 | 旧 offset | 截断到旧 offset |
| `fdatasync` 后、CAS 前 | 比 offset 多完整且持久的 chunk | 旧 offset | 截断后重传 |
| CAS 后、响应前 | 新长度且已持久 | 新 offset | 客户端旧 offset 重试得到 409 |

数据库 offset 是已确认协议进度，暂存文件超出 offset 的尾部一律视为未提交数据。

### 8.4 整机掉电语义

V1 在每个 chunk 后调用 `fdatasync()`，再提交 MySQL offset。这样 PATCH 响应的语义简单且明确：

> 返回的 `Upload-Offset` 对应一段已经持久化的数据；服务恢复后不会要求客户端回退到更早的 offset。

整机重启后执行：

```text
actual_size = stat(temp).size
actual_size > committed_offset  → truncate(temp, committed_offset)
actual_size == committed_offset → 正常恢复
actual_size < committed_offset  → 不变量损坏，标记 FAILED
```

如果客户端提供了期望 BLAKE3，最终 Hash 不匹配时必须失败，不能发布对象。

这一选择会增加同步写延迟，但 V1 的默认 chunk 是 MB 级而不是 KB 级，可以摊薄固定同步成本。必须实测不同 chunk 大小下的吞吐和 P99 延迟；如果同步确实成为瓶颈，再演进为：

- 多会话 group commit；
- 单独维护 `received_offset` 与 `durable_offset`，只向客户端承诺 durable offset；
- 允许客户端显式选择弱耐久模式。

group commit 会引入双 offset、批次失败和唤醒协作，必须由性能数据证明值得，V1 不提前实现。

## 9. BLAKE3 状态与恢复

正常上传时：

```text
chunk
→ 写入暂存文件
→ 更新内存中的 blake3_hasher
→ fdatasync
→ 推进 offset
```

这样每个字节只经过一次顺序写和一次 Hash 更新。

不把 `blake3_hasher` 内部结构直接序列化到 MySQL：

- 它是第三方库内部状态，不是稳定的持久化格式。
- 版本升级可能使历史状态不可读。
- 数据库会与具体 Hash 库 ABI 耦合。

进程重启后，第一次恢复该会话时：

```text
读取 [0, committed_offset)
→ 重建 BLAKE3 状态
→ 继续增量上传
```

重启恢复会额外读取一次已上传前缀，但这是低频故障成本；正常链路仍然没有完成后的第二次全文件读取。

当前 `StreamUploader` 析构时会删除未 finalize 的临时文件，这与断点续传冲突。可靠上传阶段应将其演进为显式生命周期的 `UploadWriter`：

- 普通请求失败只回滚本次未提交尾部，不删除整个会话。
- 只有 abort、expire 或创建失败才删除暂存文件。
- 支持从已有 offset 恢复并重建 Hasher。
- chunk 写入、同步或 MySQL 条件更新任一步确定失败后，丢弃当前 Hasher 状态；下次请求从数据库确认的 `committed_offset` 重建，不能继续使用已经吸收未提交字节的 Hasher。若数据库提交结果未知，则先重新查询，再决定保留还是截断尾部。

## 10. 完成上传与耐久化提交

complete 是整个系统最重要的事务边界。

### 10.1 完成流程

```text
1. 获取 session mutex
2. 校验 state == UPLOADING
3. 校验 committed_offset == total_size
4. 条件更新：UPLOADING → FINALIZING
5. 得到服务端最终 BLAKE3，并与 expected_hash 比较
6. MySQL: 在 FINALIZING 状态写入 content_hash
7. fdatasync(temp_fd)（通常已由最后一个 PATCH 完成，仍作为防御性检查）
8. ObjectStore 通过 link/EEXIST 原子发布或复用
9. fsync(object_parent_dir_fd)
10. MySQL: FINALIZING → COMPLETED
11. unlink(temp_path)
12. 返回成功
```

关键原则：

```text
先让物理对象耐久
再提交 COMPLETED 元数据
最后清理临时名字
```

文件系统和 MySQL 之间没有跨资源事务。这里不引入 XA 或自制两阶段提交，而是选择可恢复的操作顺序：

- 先提交 MySQL、后提交对象：可能产生数据库指向不存在对象的坏引用，不可接受。
- 先提交对象、后提交 MySQL：最多产生孤儿对象，可以由恢复流程接管或由 GC 回收，可接受。

`content_hash` 必须在对象发布前写入 `FINALIZING` 记录。否则对象发布后、`COMPLETED` 提交前一旦进程崩溃，恢复程序不知道应该检查哪个对象路径。临时文件也必须保留到 `COMPLETED` 提交之后，作为恢复和重新发布的最后兜底。

### 10.2 `fdatasync`、`link`、目录 `fsync` 分工

```text
fdatasync(temp_fd)
```

保证文件内容以及读取内容所必需的元数据（例如文件长度）进入持久存储。

```text
link(temp, object)
```

保证正式对象目录项以“不存在或完整存在”的方式原子出现，并且目标已存在时不覆盖。

```text
fsync(object_parent_dir_fd)
```

保证新目录项本身进入持久存储。只同步文件并不能保证包含它的目录项已经落盘。

如果 `objects/ab/cd` 是本次新建的目录，严格耐久模式还应同步每一级新目录的父目录。临时文件删除后是否同步临时目录只影响垃圾清理，不影响正式对象正确性。

所有 `fdatasync/fsync` 都可能阻塞，最终必须在磁盘 I/O 工作线程中执行，不能直接阻塞 Tudou EventLoop。

### 10.3 FINALIZING 恢复

MySQL 先记录 `FINALIZING`，使崩溃恢复能够判断完成流程已经开始。

| 恢复时观察 | 恢复动作 |
|---|---|
| `content_hash` 为空、temp 存在 | 重新计算 Hash，并继续完成 |
| `content_hash` 已记录、temp 存在、object 不存在 | 重新校验并发布 |
| `content_hash` 已记录、object 已存在 | 校验对象类型和长度，标记完成，再清理 temp |
| temp 不存在、object 已存在 | 校验后标记完成 |
| temp 不存在、object 不存在 | 标记 FAILED，记录错误 |

complete 重试读取到 `COMPLETED` 时直接返回已保存的 `content_hash`，不重复执行发布。

## 11. 并发模型

需要区分三类并发控制：

### 11.1 同一会话

必须串行：

- append 与 append；
- append 与 complete；
- complete 与 abort。

使用会话级 mutex，不使用全局大锁。MySQL 条件更新作为第二层一致性检查。

### 11.2 不同会话

可以并行写入不同暂存文件。MySQL 连接不能由多个工作线程同时使用，因此通过有上限的连接池为一次数据库操作独占借出连接。

连接池大小必须与文件工作线程数和 MySQL `max_connections` 协调，获取连接要有超时，不能无限等待。文件写入、Hash 和同步均在数据库事务外完成；条件更新只执行一条短 SQL，不使用 `SELECT ... FOR UPDATE` 跨越慢速文件 I/O。这样既缩短行锁持有时间，也避免一个大文件上传长期占用数据库连接。

### 11.3 相同内容的不同会话

两条上传可以独立完成并得到相同 BLAKE3。最终由 `ObjectStore::commit()` 的 `link/EEXIST` 仲裁：

- 一个返回 `Created`；
- 其他返回 `Reused`；
- 物理对象只保留一份。

## 12. EventLoop 与工作线程边界

可靠上传 V1 先把协议和恢复语义做正确，但最终目标仍然要求：

```text
磁盘 write
MySQL
BLAKE3 大块计算
fdatasync / fsync
```

不能阻塞 Tudou EventLoop。

当前 Tudou Handler 是同步请求—响应模型。演进分两步：

1. 先增加请求体上限，用有界 chunk 消除 `O(文件大小)` 内存风险。
2. 再增加 async/streaming route：EventLoop 只接收网络数据，把磁盘任务提交到工作线程，任务完成后回到连接所属 EventLoop 发送响应。

不能在线程池执行完后直接从任意线程操作连接；响应发送必须回到连接所属 EventLoop，维持 one loop per thread 的线程归属。

下载方向单独设计：

- 支持 `Range` 和 `206 Partial Content`。
- 明文连接可评估非阻塞 `sendfile`，正确处理 partial write 和 `EAGAIN`。
- HTTPS 不能简单宣称普通 `sendfile` 零拷贝；没有 kTLS 时需要走 TLS 用户态加密路径。

## 13. 错误映射

| 场景 | HTTP 状态 |
|---|---:|
| 创建成功 | `201 Created` |
| 查询成功 | `200 OK` |
| chunk 成功 | `204 No Content` |
| complete 成功或幂等重试 | `200 OK` |
| offset 不匹配 | `409 Conflict` |
| 非法长度、Header 或状态 | `400 Bad Request` |
| chunk 超过上限 | `413 Payload Too Large` |
| Content-Type 不支持 | `415 Unsupported Media Type` |
| 会话不存在 | `404 Not Found` |
| 会话已过期 | `410 Gone` |
| 最终 Hash 不一致 | `422 Unprocessable Content` |
| 磁盘、MySQL 或必要依赖暂时失败 | `503 Service Unavailable` |

不要把所有异常都转换为 `500`。客户端必须能够区分“修改请求后重试”和“稍后原样重试”。

## 14. 测试矩阵

### 14.1 单元测试

- 会话创建默认 offset 为 0。
- offset 精确匹配时推进。
- offset 落后或超前时状态和文件都不变。
- chunk 超过上限或超过总长度时拒绝。
- CAS 失败时不返回成功。
- complete 未达到总长度时拒绝。
- complete 重复调用返回同一结果。
- Hash 不匹配进入 FAILED，不发布对象。
- 过期和终止只能执行一次。

### 14.2 文件与 MySQL 恢复测试

- 文件写完、offset 未更新：重启后截断多余尾部。
- offset 已更新、响应丢失：重试不重复追加。
- FINALIZING + temp 存在：可以继续完成。
- FINALIZING + object 存在：恢复为 COMPLETED。
- 物理对象成功、MySQL 完成提交前崩溃：恢复或产生可回收孤儿，不产生坏引用。
- 同内容并发完成：一个 Created，其余 Reused。

### 14.3 HTTP 集成测试

- 创建 → 多次 PATCH → HEAD → complete → 下载。
- 上传中断后新客户端从 offset 恢复。
- 旧 offset 重试返回 409 和正确 offset。
- 超大 PATCH 在 Tudou 完整缓冲前返回 413。
- 服务重启后继续上传。
- 过期会话返回 410。

### 14.4 性能与资源测试

记录而不是只描述：

- 1 GB、10 GB 文件上传时的 RSS 峰值。
- 不同 chunk 大小下的吞吐、请求数和 MySQL 开销。
- 并发上传数与吞吐、RSS、磁盘队列深度的关系。
- 连接池等待时间、活跃连接数和慢查询。
- BLAKE3 占用的 CPU 比例。
- `fdatasync + directory fsync` 的完成延迟分位数。
- 每个 PATCH 的 `fdatasync + MySQL commit` 延迟分位数。
- Created 与 Reused 的完成延迟差异。
- 进程中断后恢复所需时间和额外读取字节数。

目标是证明：

```text
RSS 与单文件大小无关
```

而不是只给出一次峰值 RPS。

## 16. 面试问答

### 为什么不直接上传一个 10 GB HTTP Body？

当前 Tudou 会完整缓冲请求体，内存占用是 `O(文件大小)`；连接中断还要从头重传。有界 PATCH 将内存限制为 `O(并发请求数 × chunk 上限)`，并允许从服务端 offset 继续。

### 为什么选择顺序 offset，不做并行分片？

顺序 offset 不需要分片合并，可以持续增量计算标准 BLAKE3，磁盘只做顺序写，状态机也更容易恢复。并行分片要维护缺失 bitmap、乱序写、合并或最终全文件重读，只有性能数据证明必要时才值得增加。

### 重复 PATCH 为什么不会重复写？

服务端只接受 `request_offset == committed_offset`。响应丢失后，客户端携带旧 offset 重试会得到 409 和当前 offset，文件状态不变，然后通过 HEAD 恢复。

### 为什么文件写入和 MySQL 更新不能放在一个事务里？

MySQL 事务不能原子覆盖应用服务器本地文件系统写入。系统通过操作顺序和恢复规则获得一致性：文件允许领先数据库，恢复时按数据库 offset 截断；完成时先持久化物理对象，再提交完成元数据，最多产生可回收孤儿，不产生坏引用。

### 为什么 chunk 要逐块 fdatasync？

因为 MySQL offset 一旦返回给客户端，就代表服务端承诺此前数据已经接收。如果先提交 offset、文件数据却还只在页缓存中，掉电后可能出现“数据库说收到了，文件实际没有”的坏状态。V1 采用 `write → fdatasync → MySQL commit → response`，用 MB 级 chunk 摊薄同步成本。只有基准测试证明它是瓶颈时，才引入更复杂的 group commit 和双 offset。

### 为什么既有 link 还需要 fsync？

`link` 保证新目录项原子创建且不覆盖已有对象，解决并发可见性；`fdatasync` 保证文件内容持久，目录 `fsync` 保证新名字持久。三者解决的是不同问题。

### 为什么使用 MySQL？

虽然物理对象存储是单机的，但 FileLink 后续存在用户、逻辑文件、分享链接、权限和审计等关系数据。MySQL/InnoDB 可以统一承载事务、唯一约束、行锁和条件更新，也更贴近团队系统的部署与运维方式。代价是必须处理连接池、超时和数据库不可用，不能把它描述成“免费扩展”。

### 为什么暂时不用 Redis？

上传 offset 和状态属于强一致数据，直接查询 MySQL 更简单；缓存 offset 反而可能让客户端从错误位置继续。等登录会话、限流或热点分享链接出现后，再使用 Redis，并确保 Redis 故障只影响性能或降级能力，不影响文件和元数据正确性。
