# 文件领域模型

## 边界

FileLink 将一次上传、用户可见文件和物理字节分开建模：

```text
User 1 --- N File N --- 1 Object
                 ^
          UploadSession（完成时创建 File）
```

- **User** 是身份与访问控制的主体。
- **File** 是用户拥有的逻辑文件，保存显示名称和归属；它不是磁盘文件。
- **Object** 是以 BLAKE3 摘要定位的不可变字节序列；多个 `File` 可以引用同一个 `Object`。
- **UploadSession** 是短生命周期的传输任务，只在成功完成后产出一个 `File`。在认证功能接入前，会话可以暂时没有归属用户；`File` 始终必须归属于用户。

磁盘路径始终由 `ObjectStore` 的 `content_hash` 推导，数据库不保存可变的绝对路径。

## 不变量

1. 每个 `File` 必须同时属于一个 `User` 并引用一个 `Object`。
2. 一个 `Object` 的字节数和内容哈希一经发布不得修改。
3. `objects.ref_count` 等于引用该对象的 `files` 行数；创建或删除逻辑文件时必须在同一数据库事务中更新它。
4. `UploadSession` 只有在对象已原子发布、对象引用已增加且 `File` 已创建后，才可转为 `COMPLETED`。
5. 下载入口以 `file_id` 为准，先验证用户对 `File` 的权限，再解析其 `content_hash`；不得向最终用户暴露按哈希的无鉴权下载。

## 上传、秒传与删除

上传完成时，服务先通过 `ObjectStore` 发布或复用哈希对象，再在一个 MySQL 事务中创建/锁定 `Object`、增加 `ref_count`、创建 `File` 并完成会话。文件系统与数据库无法构成单一事务：若数据库提交失败，已发布但无数据库引用的对象是安全的孤儿，由宽限期后的巡检任务回收。

秒传沿用同一完成流程：确认既有对象的大小与摘要后，直接创建新的 `File` 并增加引用，不必上传内容。

删除只移除 `File` 并递减引用。引用归零的对象标为 `PENDING_DELETE`，由回收任务删除物理对象及其数据库记录；重新引用时必须在同一对象行锁下取消待删除状态。

## 服务职责

- `ObjectStore`：只处理哈希对象的路径、原子发布和物理删除。
- `UploadService`：只处理 TUS 会话、分片、哈希和完成编排。
- 后续 `FileService`：创建、列表、删除和授权下载逻辑文件。
- `ApiRouter`：解析 HTTP 请求、鉴权并调用服务，不直接访问数据库或文件系统。
