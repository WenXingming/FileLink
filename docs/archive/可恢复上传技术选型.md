# FileLink 可恢复上传技术选型

> 状态：已采纳  
> 日期：2026-07-05  
> 适用范围：单机 FileLink V1

## 1. 结论

FileLink 采用以下组合：

```text
浏览器
  └── tus-js-client：parallelUploads=1，chunkSize=8 MiB
            │          切块、重试、暂停、恢复、进度
            │
            │ tus 1.0
            v
FileLink / Tudou
  ├── tus Core：HEAD、PATCH、OPTIONS
  ├── Creation：POST
  ├── Expiration：过期时间与后台清理
  ├── Termination：DELETE（后续实现）
  └── FileLink 业务：MySQL 会话、BLAKE3、内容寻址、秒传
```

选择的是“兼容 tus 的最小服务端”，不是：

- 自定义一套私有分片协议；
- 引入 `tusd` 独立进程；
- 实现 tus 全部扩展；
- 把文件保存成多个 chunk 后再合并；
- 引入 MinIO/S3 替代本地内容寻址存储。

一句话概括：

> 用 tus 标准和 `tus-js-client` 消除客户端重复代码，FileLink 只保留无法外包的服务端持久化与业务一致性。

## 2. 目标与约束

当前 FileLink 的定位是面向团队内部模型权重、数据集和安装包的单机大文件可靠分发平台，技术选型必须满足：

1. 上传数 GB 文件时不把整个文件放入内存。
2. 网络中断、页面刷新或服务重启后能够继续上传。
3. 重试不能重复写入数据。
4. 未完成上传能够过期清理。
5. 服务端仍然负责 BLAKE3 校验和内容寻址发布。
6. 继续使用 Tudou 作为 HTTP 服务框架。
7. MySQL 是上传状态的事实来源，Redis 不参与正确性链路。
8. 尽可能使用成熟库，但优化的是系统总复杂度，而不只是本仓库代码行数。

最后一条很重要：少写 300 行协议代码，却增加一个独立服务、Hook 重试和跨进程一致性，并不是真正的简单。

## 3. 候选方案

### 3.1 自定义顺序 offset 协议

形式与 tus 类似：

```http
POST  /uploads
HEAD  /uploads/{id}
PATCH /uploads/{id}
```

优点：

- 服务端只实现项目需要的行为。
- 协议可以自由命名和调整。
- 容易与现有 MySQL 状态机、ObjectStore 集成。

缺点：

- 浏览器端必须自己实现切块、重试、断点记录和恢复。
- 需要自行定义错误语义和兼容性。
- 本质上会重新设计一个缩水版 tus，却不能复用成熟客户端。

结论：不选。

旧设计已经证明顺序 offset 的服务端模型是正确方向，但没有理由继续维护私有线协议。

### 3.2 tus 标准 + `tus-js-client` + FileLink 最小服务端

客户端由 `tus-js-client` 负责：

- 按 FileLink 配置的 `chunkSize` 切块并发送；
- 自动重试暂时性网络错误；
- `HEAD` 查询服务端 offset；
- 页面刷新后寻找并恢复历史上传；
- 暂停、继续和进度回调。

FileLink 服务端负责：

- 创建上传资源；
- 校验 tus 请求头和 offset；
- 顺序追加到单个 `.part` 文件；
- 持久化 MySQL 会话；
- 处理并发、崩溃恢复和过期清理；
- 完整文件 BLAKE3 校验；
- 发布到内容寻址 ObjectStore；
- 创建逻辑文件和处理秒传。

优点：

- 复用成熟浏览器客户端，不写自定义前端上传器。
- 协议行为有公开规范，容易测试和解释。
- 服务端仍在 Tudou 中，保留 FileLink 的可靠性设计和 C++ 工程价值。
- 顺序 offset 只需要一个临时文件和一个单调递增 offset。
- 没有分片表、分片目录、bitmap 和最终合并。

缺点：

- C++ 端没有成熟、可直接嵌入 Tudou 的官方 tus 服务端库。
- 必须实现并测试一小部分协议头和状态码。
- 宣称兼容 tus 后，行为必须遵守规范，不能随意修改语义。

结论：选择。

### 3.3 `tusd` 独立服务

`tusd` 是 Go 编写的官方参考服务端，能够直接通过 Docker 运行，并使用本地磁盘等存储后端。

架构会变为：

```text
浏览器 ──上传──> tusd ──Hook──> FileLink
浏览器 ──业务──> FileLink
```

优点：

- tus 协议和文件接收代码最少。
- 官方实现成熟，锁、存储后端和监控能力完整。

缺点：

- 新增 Go 服务进程和独立配置。
- tusd 持有传输状态，FileLink 持有业务状态，形成两个事实来源。
- 完成上传后需要 Hook 才能进入 BLAKE3、ObjectStore 和逻辑文件流程。
- Hook 可能并发或乱序，部分后处理事件不会自动可靠重试，因此 FileLink 仍要实现幂等、任务记录和失败补偿。
- 上传流量绕过 Tudou，削弱 Tudou 与 FileLink 的项目关联。

结论：不选。

如果未来目标变成“尽快交付普通业务产品”，而不再要求 Tudou 承载核心上传链路，可以重新评估 tusd；当前单机深挖阶段不合适。

### 3.4 S3 Multipart Upload / MinIO

S3 Multipart Upload 将文件拆成带 part number 的多个对象，可以乱序、并行上传，最终由存储服务合并。

优点：

- SDK 和生态成熟。
- 支持并行上传，适合远程对象存储和高带宽场景。
- 应用服务器可以通过预签名 URL 避免中转文件数据。

缺点：

- FileLink 当前明确采用本地 POSIX 文件系统，而不是 S3。
- 引入 MinIO 会把内容寻址发布、`link()` 原子去重等核心设计交给外部存储。
- 服务端需要维护 part number、ETag、完成列表和未完成 multipart 清理。
- 并行分片的状态空间明显大于单调 offset。

结论：不选。

当项目演进为多机部署或使用云对象存储时，S3 Multipart Upload 才是更自然的选择。

### 3.5 Resumable.js 式编号分片

该类客户端把文件切为多个有编号的 chunk，并发发送给服务端。Resumable.js 默认允许三个 chunk 同时上传，并通过逐 chunk 的探测请求恢复进度。

优点：

- 天然支持多个 chunk 并行上传。
- 单个分片失败时只重传该分片。
- 服务端可以自由选择“分片文件后合并”或“按 offset 直接写入预分配文件”。

缺点：

- 仍然没有可直接嵌入 Tudou 的通用服务端实现。
- 服务端要维护 chunk 集合或 bitmap、重复请求、缺失检查和并发写入。
- 如果每个 chunk 独立保存，完成时需要合并并产生额外完整文件 I/O。
- 如果使用并发 `pwrite()` 避免合并，则要正确处理目标区间、文件空洞、分片状态与磁盘写入的一致性。
- 完整 BLAKE3 通常还要按文件顺序重新读取。

结论：不选。

不选择它不是因为并发分片“没有技术含量”，而是它把复杂度放在乱序写入和 chunk 集合上，与 FileLink 当前希望深入的耐久 offset、顺序 I/O 和内容寻址发布不一致。V1 也没有性能数据证明单流顺序上传不足，因此不提前承担这部分复杂度。

### 3.6 `Content-Range + PUT` 私有约定

HTTP 允许客户端和服务端通过私有约定实现 Partial PUT，但 RFC 9110 明确指出其支持并不一致，依赖双方约定，不能提供 tus 生态和成熟客户端。

结论：不选。

### 3.7 IETF Resumable Uploads for HTTP

IETF HTTP 工作组正在制定通用的可恢复上传标准。它同样使用独立 upload resource，支持查询 offset、追加数据和取消上传，长期看有机会成为比 tus 更通用的 HTTP 标准。

截至 2026-07-05：

- 最新版本是 `draft-ietf-httpbis-resumable-upload-11`；
- 文档状态仍是 Active Internet-Draft，不是正式 RFC；
- 草案通过 interop version 处理迭代期间的破坏性变化；
- `tus-js-client` 只有实验性草案支持，公开 API 当前列出的版本落后于最新草案。

结论：跟踪，但 V1 不选。

现在实现会把 FileLink 绑定到仍可能变化的报文语义和兼容版本。待协议成为 RFC、浏览器客户端稳定支持后，再评估从 tus 迁移；底层单调 offset、暂存文件和 MySQL 状态机仍可复用。

## 4. 评分

评分采用 1～5 分，越高越符合当前 FileLink。

| 方案 | 客户端复用 | 服务端简洁 | Tudou 集成 | 单机存储适配 | 项目可讲性 | 总体 |
|---|---:|---:|---:|---:|---:|---:|
| 私有 offset | 1 | 4 | 5 | 5 | 3 | 18 |
| tus 最小服务端 | 5 | 4 | 5 | 5 | 5 | **24** |
| tusd sidecar | 5 | 2 | 1 | 3 | 3 | 14 |
| S3 Multipart | 5 | 2 | 2 | 1 | 4 | 14 |
| 编号分片合并 | 4 | 2 | 4 | 3 | 3 | 16 |
| Partial PUT | 2 | 4 | 5 | 5 | 2 | 18 |
| IETF 草案 | 2 | 3 | 5 | 5 | 4 | 19 |

评分不是通用优劣排名，只针对“单机、本地文件系统、Tudou、内容寻址”的当前约束。

## 5. tus 兼容范围

### 5.1 V1 实现

| 能力 | HTTP | 用途 |
|---|---|---|
| Core / 查询 | `HEAD /uploads/{id}` | 返回当前 `Upload-Offset` |
| Core / 追加 | `PATCH /uploads/{id}` | 从指定 offset 追加字节 |
| 能力发现 | `OPTIONS /uploads` | 返回版本、扩展和大小上限 |
| Creation | `POST /uploads` | 创建上传资源 |
| Expiration | 响应 `Upload-Expires` | 告知客户端未完成上传的有效期 |

所有 tus 请求和响应按规范携带：

```http
Tus-Resumable: 1.0.0
```

`PATCH` 使用：

```http
Content-Type: application/offset+octet-stream
Upload-Offset: <client-offset>
```

只有当客户端 offset 等于服务端 offset 时才允许写入；不匹配返回 `409 Conflict`，并且不能修改资源。

### 5.2 后续实现

| 扩展 | HTTP | 用途 |
|---|---|---|
| Termination | `DELETE /uploads/{id}` | 主动终止并释放未完成上传 |

### 5.3 暂不实现

- Creation With Upload；
- Creation Defer Length；
- Checksum；
- Concatenation；
- 并行、乱序上传。

tus 本身并非只能单流上传。`tus-js-client` 可以通过 `parallelUploads > 1` 使用 Concatenation 扩展并发上传多个 partial upload。FileLink V1 主动选择 `parallelUploads = 1`，是为了先获得最小状态机；如果后续基准测试证明并行有明确收益，可以在不更换客户端协议的前提下增加 Concatenation。

不实现 Checksum 扩展，不代表不校验文件：

- tus Checksum 是单次 `PATCH` 请求级校验，而且若宣称支持，规范要求至少支持 SHA-1。
- FileLink 的 BLAKE3 是完整对象身份和最终完整性校验。
- HTTPS/TCP 已负责传输层错误检测；V1 不为每个 chunk 再增加一套摘要协议。

如果以后确有分片损坏诊断需求，再单独评估 Checksum 扩展。

## 6. tus 与 FileLink 业务边界

tus 只负责“字节可靠到达暂存文件”，不负责 FileLink 的业务完成。

```text
最后一个 PATCH 成功
→ committed_offset == total_size
→ 上传传输完成
→ 后台/工作线程进入 FINALIZING
→ 服务端计算或确认 BLAKE3
→ ObjectStore 原子发布
→ MySQL 标记 COMPLETED
→ 逻辑文件可见
```

不增加自定义的：

```http
POST /uploads/{id}/complete
```

原因是 tus 以 `Upload-Offset == Upload-Length` 表达传输完成，额外 complete 会让客户端和协议状态出现两套完成语义。

最终 BLAKE3 和 `ObjectStore::commit()` 可能耗时，不能阻塞 Tudou EventLoop，也不应让最后一个 `PATCH` 长时间等待。客户端在 `tus-js-client` 的上传成功回调后，通过 FileLink 业务接口查询：

```http
GET /api/uploads/{id}
```

业务状态可能是：

```text
FINALIZING | COMPLETED | FAILED
```

这不是 tus 协议扩展，而是 FileLink 自己的业务查询接口。

必须显式配置 `tus-js-client` 的 `chunkSize`，V1 初始值取 8 MiB，并由压测决定是否调整。当前 Tudou 会在进入业务 Handler 前缓冲一次 PATCH 的完整请求体，因此服务端还必须独立限制 `Content-Length <= maxChunkBytes`；不能只信任客户端配置。

## 7. 秒传不属于 tus

秒传发生在创建 tus 上传之前：

```text
客户端计算 BLAKE3 + size
→ POST /api/uploads/preflight
    ├── 对象存在：创建 logical_file，返回 instant=true
    └── 对象不存在：返回 instant=false，启动 tus-js-client
```

tus 上传创建时仍在 `Upload-Metadata` 中携带经过 Base64 编码的：

- `filename`；
- `expected_hash`。

客户端 Hash 只用于秒传查询和最终比对。真正上传新对象时，服务端仍必须根据收到的数据验证完整 BLAKE3，不能信任客户端声明。

## 8. 数据与文件模型

V1 继续采用：

```text
MySQL upload_sessions
  - upload_id
  - state
  - total_size
  - committed_offset
  - expected_hash
  - content_hash
  - expires_at

storage/uploads/<upload-id>.part
storage/objects/<hash-prefix>/<hash>
```

关键点：

- 一个上传只有一个 `.part` 文件。
- `committed_offset` 单调递增。
- 不建立 `upload_chunks` 表。
- 不为每个请求保存独立分片文件。
- 不执行最终分片合并。
- Redis 不保存 offset。

这正是 tus 对当前项目最有价值的地方：客户端可以按块发送，但服务端不必采用“多分片存储”架构。

## 9. 依赖集成方式

`tus-js-client` 是前端依赖，通过 npm 固定版本，不通过 CMake `FetchContent`：

```text
frontend/package.json
└── tus-js-client
```

C++ 服务端不新增 tus 依赖，只按照协议实现少量 HTTP 适配。已有依赖继续各司其职：

- Tudou：HTTP 与连接；
- MySQL Connector/C++：上传会话；
- BLAKE3：内容摘要；
- spdlog：日志；
- GTest：状态机和协议测试。

避免增加一个名义上的 `TusServer` 第三方库，却还需要大量适配 Tudou、MySQL 和 ObjectStore。

## 10. 实施边界

技术选型不意味着一次实现全部能力。按小步推进：

1. 实现 MySQL `upload_sessions` migration，以及创建、查询和 offset CAS。
2. 为 Tudou 增加请求体上限，在完整 body 进入业务 Handler 前拒绝超大 PATCH。
3. 实现 tus `OPTIONS`、Creation `POST` 和 Core `HEAD`，先打通会话创建与查询。
4. 实现 Core `PATCH`、单 `.part` 文件顺序写入、`fdatasync` 和 offset 提交。
5. 实现最后一个 PATCH 后的 `FINALIZING`、BLAKE3 校验和 ObjectStore 发布。
6. 接入 `tus-js-client`，验证网络中断、响应丢失、页面刷新和服务重启恢复。
7. 实现 Expiration、Termination、启动恢复与后台清理。
8. 完成 chunk size 和单流/并行性能基准，再决定是否增加 Concatenation。

第一步的验收标准：

- migration 能创建 `upload_sessions` 表。
- 新会话状态为 `UPLOADING`，offset 为 0。
- `find` 能在进程重启后读取同一会话。
- offset CAS 只有在旧 offset 和状态都匹配时成功。
- 本步骤不增加 HTTP Handler、分片表、分片文件和合并逻辑。

## 11. 面试回答

### 为什么选择 tus，而不是自己设计分片协议？

服务端最终仍然是顺序 offset 状态机，但 tus 给出了标准 HTTP 语义，并且可以直接复用 `tus-js-client` 的切块、重试和浏览器恢复能力。这样避免维护私有客户端协议，FileLink 只实现与本地持久化和业务一致性有关的部分。

### 既然强调使用库，为什么不用 tusd？

tusd 减少了单进程内的协议代码，但增加了独立 Go 服务、Hook 通信和两套上传状态。FileLink 上传完成后还要执行 BLAKE3、内容寻址发布和 MySQL 状态迁移，而 Hook 需要额外处理乱序、幂等与失败补偿。对当前单机项目来说，总复杂度反而更高。

### 为什么不做并行分片？

当前没有性能数据证明单流上传是瓶颈。顺序 offset 只维护一个单调进度和一个临时文件，不需要分片表、缺失 bitmap、合并和乱序 Hash。先获得可证明的正确性，再根据吞吐测试决定是否实现 tus Concatenation 或 S3 Multipart。

### tus 是否替代了 FileLink 的核心技术？

没有。tus 只规定如何恢复 HTTP 上传。FileLink 仍然负责文件与 MySQL 的提交顺序、`fdatasync` 耐久边界、崩溃恢复、BLAKE3、内容寻址去重、逻辑文件、秒传和垃圾回收，这些才是项目的业务与存储核心。

### 为什么最后一个 PATCH 后不再调用 complete？

tus 已用 `Upload-Offset == Upload-Length` 定义传输完成。自定义 complete 会制造第二套完成语义。FileLink 将传输完成和业务发布分开：最后一个 PATCH 后进入 `FINALIZING`，客户端再查询业务状态，直到对象变为 `COMPLETED`。

## 12. 深度对比：tus 与 Resumable.js

### 12.1 两者真正的差异

V1 比较的不是“tus 永远单流”和“Resumable.js 永远并行”，而是两种服务端状态模型：

| 维度 | tus 顺序 offset | Resumable.js 编号分片 |
|---|---|---|
| 进度事实 | 单调 `committed_offset` | 已完成 chunk 集合或 bitmap |
| 写入布局 | 单文件顺序追加 | 分片文件，或按 offset 并发 `pwrite()` |
| 恢复查询 | 一次 `HEAD` | 查询多个 chunk 是否存在 |
| 重复请求 | offset 不匹配即拒绝 | 同一 chunk 必须允许重复到达 |
| 最终处理 | 不需要合并 | 分片文件要合并；`pwrite` 方案要检查空洞 |
| BLAKE3 | 正常链路可增量计算 | 乱序到达通常需要完成后顺序扫描 |
| 并发扩展 | 后续可加 Concatenation | 客户端原生并发 chunk |

Resumable.js 的并发模型并不是普通 CRUD，也具有并发一致性和崩溃恢复方面的技术深度；只是这些问题不是当前 FileLink 最想投入复杂度的方向。

### 12.2 “Resumable.js 必然双倍 I/O”并不准确

最直观的实现会分别保存 chunk：

```text
chunk-1 + chunk-2 + ... + chunk-n
→ 读取所有 chunk
→ 写出完整临时文件
```

这种实现确实产生接近一个完整文件的额外读写和完成时 I/O 峰值。

但是服务端也可以预分配单个临时文件，再根据 chunk number 计算 offset，并发执行：

```text
pwrite(temp_fd, chunk, chunk_offset)
```

这样可以避免最终合并，代价是必须正确处理：

- chunk 状态提交与磁盘数据落盘的先后关系；
- 相同 chunk 的重复和并发写入；
- 缺失区间、文件空洞和越界；
- 多个写入者的同步；
- 最终全文件 BLAKE3 扫描。

因此“不选 Resumable.js”的理由不是它必然双倍 I/O，而是无论采用哪种落盘方式，都比单调 offset 引入更多状态。

### 12.3 “单个 TCP 一定跑满带宽”也不准确

单连接吞吐受 RTT、丢包、拥塞控制、接收窗口、代理限制、磁盘速度和同步写延迟影响。多个连接在部分高延迟或丢包环境下可能提高总吞吐，但也会：

- 增加连接、内存和调度开销；
- 加剧同机磁盘写入竞争；
- 对其他用户产生带宽公平性问题；
- 扩大服务端状态空间。

FileLink 面向团队内部网络，单流更可能已经足够，但这只是待验证假设。`tus-js-client` 文档也建议在真实环境评估 `parallelUploads`；其维护者在普通浏览器场景没有观察到平均用户的性能提升。

### 12.4 为什么 V1 仍选择 tus 顺序模式

FileLink V1 希望深入的是：

```text
POSIX 持久化
→ fdatasync 耐久边界
→ MySQL offset 提交
→ 崩溃恢复
→ BLAKE3 内容寻址
→ link/fsync 原子发布
```

顺序 tus 只需要一个 `.part` 文件和一个单调 offset，可以用较小状态空间证明请求幂等与崩溃恢复，也不会产生最终分片合并。

这不是宣称 tus 对所有系统都优于 Resumable.js，而是在 FileLink 当前业务、单机边界和项目目标下更匹配。

### 12.5 用数据决定是否升级为并行

V1 完成后测试：

- 文件大小：1 GiB、10 GiB、50 GiB；
- `chunkSize`：8、16、32、64 MiB；
- 网络：局域网，以及模拟不同 RTT 和丢包率；
- 负载：单上传和多个用户并发上传；
- 指标：吞吐、CPU、内存、P99、磁盘写放大和恢复时间。

只有当顺序上传不能接近网络或磁盘瓶颈，并且并行模式实测有稳定收益时，才实现 tus Concatenation。这样保留演进能力，又不为假设中的瓶颈预付复杂度。
