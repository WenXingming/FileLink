# 可恢复上传与内容去重

FileLink 的上传不是“收到一个 HTTP 请求，就把整个文件写进数据库”。它把一次大文件传输拆成可恢复的分片过程，最后才把已经校验过的字节发布为 Object，并为当前用户创建 File。

这一拆分同时解决三件事：弱网中断后继续上传、上传过程中不持有完整文件内存、相同内容只保存一份物理字节。

## 先记住主流程

```text
POST 创建 UploadSession
        │
        ├─ 数据库命中秒传：Object +1 → 创建 File → COMPLETED
        │
        └─ 数据库未命中：保持 UPLOADING → PATCH 分片
                                      │
                                收到最后一片
                                      ▼
                                 FINALIZING
                                      │
                         校验哈希、原子发布/复用 Object
                                      │
                                      ▼
                     事务：Object +1、创建 File、会话 COMPLETED
```

这里的核心边界是：`UploadSession` 描述传输，Object 描述不可变字节，File 描述用户最终拥有的文件。三者不能合并，否则断点续传、去重和权限会缠在一起。

## 为什么使用 TUS 分片协议

普通 `POST /upload` 有一个简单的问题：网络在传到 9 GB 时中断，服务端和客户端都不知道已经可靠保存了多少内容，通常只能重传完整文件。

FileLink 通过 TUS 风格接口让“已提交字节数”成为双方共享的事实：

| 请求 | 路径 | 作用 |
| --- | --- | --- |
| `OPTIONS` | `/uploads` | 声明 `creation`、`expiration`、`termination` 能力 |
| `POST` | `/uploads` | 创建上传会话，携带 `Upload-Length` 与元数据 |
| `HEAD` | `/uploads/<id>` | 读取服务器确认的 `Upload-Offset` |
| `PATCH` | `/uploads/<id>` | 从指定偏移写入一个二进制分片 |
| `GET` | `/uploads/<id>` | 查询会话状态及完成后的 `file_id` |
| `DELETE` | `/uploads/<id>` | 取消仍处于上传中的会话 |

所有接口先通过 Cookie 鉴权，并按 `owner_user_id` 查询会话。其他用户既不能续传，也不能通过 `HEAD` 或 `GET` 获取上传进度。

### 偏移量如何防止重复或错位写入

客户端每次 `PATCH` 都带上 `Upload-Offset`，服务端只接受它恰好等于 `upload_sessions.committed_offset` 的请求：

```text
数据库已确认 offset = 4 MiB

客户端 PATCH offset = 4 MiB  → 接受，写入后确认 5 MiB
客户端 PATCH offset = 3 MiB  → 409 Conflict，客户端先 HEAD 再决定重试
客户端 PATCH offset + 分片长度 > Upload-Length → 400 Bad Request
```

因此 `committed_offset` 不是客户端声称的进度，而是服务端成功写入并提交后的进度。网络响应丢失时，客户端先 `HEAD` 获取这个值，再从正确位置继续，不需要猜测。

服务端对单个分片执行的顺序是：验证所属用户和偏移量 → 将分片写到 `storage/uploads/<upload-id>.part` → `fdatasync` 临时文件 → 在 MySQL 事务中更新偏移量。若数据库事务没有提交，客户端重试同一偏移会覆盖同一段字节；数据库仍不会错误地跳过未确认数据。

## 流式 BLAKE3：不把完整文件放入内存

内容哈希既用于完整性校验，也是 Object 的唯一身份。每次 `PATCH` 后，`UploadService` 将当前分片喂给该会话的 BLAKE3 hasher；最后一片到达时才输出 32 字节摘要。

```text
chunk 1 ─┐
chunk 2 ─┼─► 同一个 BLAKE3 状态 ─► 64 位十六进制 content_hash
chunk 3 ─┘
```

服务端内存中只保存活跃会话的哈希状态，而非完整文件。Tudou 在处理某个 `PATCH` 时仍会持有该请求体，但文件不会被整体读入内存；大文件的内存占用主要受单片大小限制。

哈希状态是进程内缓存，不是可靠存储：服务重启、缓存被清理或客户端从旧偏移重试时，服务会从已有 `.part` 文件读取到当前偏移，重建 hasher 后继续计算。缓存最多积累到一定数量后清理一小时未活动的条目，防止大量中断上传长期占用内存。

客户端可以在 `Upload-Metadata` 中提供 `expected_hash`。最终哈希若不匹配，会话标记为 `FAILED`，临时分片被删除；客户端无法借一个错误的声明哈希得到别人的 Object。

## 两层去重，而不是只相信客户端

### 第一层：创建会话时的秒传

若客户端提供 64 位 `expected_hash`，服务端会先创建 `UPLOADING` 会话，再尝试原子引用数据库中同哈希、同大小的 Object。`READY` 对象可以直接引用，`PENDING_DELETE` 对象会恢复为 `READY`；不存在、大小不匹配或已经进入 `RECLAIMING` 的对象不会命中秒传，会话继续保持 `UPLOADING`。

这就是秒传：客户端不发送文件字节，但系统仍会为当前用户创建新的 File，并将 Object 的 `ref_count` 加一。它不是把已有用户的文件记录暴露给新用户。

秒传的业务判定只依赖数据库，不实时检查物理文件。数据库记录与物理字节不一致属于存储一致性故障，由下载错误、监控和离线维护处理，不进入正常上传状态机。

这一优化依赖客户端提供哈希，因此普通上传路径仍必须保留最终去重。

### 第二层：发布时的最终物理去重

普通上传结束后，服务计算真实 BLAKE3 哈希，并调用 `ObjectStore::commit(partPath, hash)`。对象路径由哈希确定：

```text
storage/objects/<hash前2位>/<再2位>/<完整64位hash>
```

发布时先同步临时文件，再用 `link(tempPath, objectPath)` 原子创建正式名称：

- `link` 成功：这是第一次出现该内容，正式 Object 创建成功。
- 返回 `EEXIST`：另一个上传已经发布同一哈希，删除本次临时文件并复用现有 Object。

因此，即使两个用户同时上传相同内容，也不会产生两份正式字节。这里不依赖“先查再写”的脆弱判断，而由文件系统的原子创建结果决定唯一赢家。

## 为什么发布顺序不能颠倒

完成上传时有两个独立系统：文件系统和 MySQL，无法用一个跨系统事务同时提交。当前顺序是：

```text
1. 临时 .part 已 fdatasync
2. 发布/复用 Object（link + 目录 fsync）
3. MySQL 事务：
   - 创建或增加 objects 引用
   - 创建当前用户的 files 记录
   - UploadSession → COMPLETED，并写 completed_file_id
```

若先提交数据库再发布 Object，下载可能读到一个不存在的物理路径；所以必须先保证字节可读，再让数据库引用它。

反过来会带来一个可恢复的窗口：Object 发布成功后、MySQL 事务提交前进程崩溃，磁盘上可能有一个没有 `objects` 记录的孤儿文件。项目没有在在线上传请求中扫描整个存储，而是交给离线 `ObjectOrphanReclaimer` 发现和清理。这是用可控的后台补偿换取在线链路的简单与性能。

## `FINALIZING` 为什么存在

收到最后一片并不表示业务上已经完成：还要哈希校验、发布 Object、创建 File。因此服务先在分片事务中把会话状态写为 `FINALIZING`，再启动完成流程。

```text
UPLOADING
  │ 最后一片已持久化且偏移达到 total_size
  ▼
FINALIZING ──校验/发布/建档成功──► COMPLETED
     │
     └──任一阶段失败──► FAILED
```

取消只允许 `UPLOADING` 状态；对 `FINALIZING` 返回 `409 Conflict`。这使“删除临时文件”和“将临时文件发布为 Object”不会在正常流程中同时发生。完成后的客户端通过 `GET /uploads/<id>` 取得 `completed_file_id`，再刷新私有文件列表。

## 一个完整例子

Alice 上传一个 12 MiB 的 `video.mp4`：

1. 浏览器 `POST /uploads`，记录文件名和总大小，服务创建 Alice 的 `UploadSession(UPLOADING, offset=0)`。
2. 浏览器以 4 MiB 分片发送三次 `PATCH`。每次都带上上次服务器返回的 offset。
3. 第二次响应在网络中丢失。浏览器 `HEAD` 得到 `Upload-Offset: 8 MiB`，因此直接发送第三片，不重传整个文件。
4. 第三片写入并同步后，offset 达到 12 MiB，会话变为 `FINALIZING`。
5. 服务得到真实哈希 `H`，原子创建或复用 `Object(H)`，随后事务创建 `File(F, Alice, H, "video.mp4")`。
6. `GET /uploads/<id>` 返回 `COMPLETED` 与 `file_id=F`；文件已经可以通过私有下载接口访问。

若 Bob 上传相同内容：他可能因提交了 `H` 直接秒传，也可能正常传完后在 `link` 时发现 `EEXIST`。无论哪种路径，最终都是 Bob 的新 File 指向同一个 `Object(H)`。

## 面试时的讲述重点

“我把大文件上传拆为 TUS 会话和最终文件两个阶段。分片请求用服务端确认的 offset 驱动，网络中断后客户端通过 HEAD 恢复；哈希器随分片递增计算，避免将完整文件读进内存。完成时先用 `fdatasync + link + fsync` 原子发布内容寻址对象，`EEXIST` 自然实现并发去重；再用 MySQL 事务维护 Object 引用计数、创建用户的逻辑 File 并完成会话。这样去重共享的是字节，不共享文件所有权。”
