# 项目总览与模块地图

FileLink 是一个运行在 Linux 上的个人云文件服务：用户通过浏览器注册、登录并上传文件；系统将相同内容只保存一份物理字节，同时为每位用户创建独立的逻辑文件记录。用户可查看、下载、删除自己的文件，也可创建带过期时间的公开分享链接。

它的核心不是“按哈希公开下载”，而是三层关系：**用户拥有 File，File 引用 Object，Object 保存唯一的物理内容**。这样既能表达权限，又能完成跨用户内容去重。

## 从入口看系统

`src/main.cpp` 是组合根：它读取 `AppConfig`，创建 MySQL 连接池、对象存储、可选 Redis 缓存和各业务服务，再把路由注册到 Tudou HTTP 服务器。业务类不自行创建数据库连接或相互隐藏创建，依赖关系在这里集中可见。

```text
浏览器 / curl
       │ HTTP + Cookie
       ▼
Tudou HttpServer ──► 路由层 ──► 认证 / 上传 / 文件 / 分享服务
                                      │          │
                                      ▼          ▼
                                 MySQL       ObjectStore
                               元数据真相     本地磁盘字节
                                      │
                                      └──► Redis（可选会话缓存）
```

当前头文件依赖图有 29 个节点、62 条边且无循环依赖。`main.cpp` 指向多个模块是正常的“装配”依赖；底层的 `db/`、`ObjectStore` 不反向依赖路由或业务模块。

## 数据与存储边界

MySQL 是业务元数据的唯一真相来源：

- `users`：账户；`user_sessions`：会话令牌的哈希及过期时间。
- `upload_sessions`：临时传输状态，成功后以 `completed_file_id` 指向结果。
- `objects`：由 BLAKE3 内容哈希标识的唯一物理内容，维护 `ref_count` 和回收状态。
- `files`：用户可见的逻辑文件，含展示名、所属用户和 `content_hash`。
- `shares`：文件的公开授权，保存分享令牌哈希、过期和撤销状态。

磁盘只保存对象字节与上传中的分片文件。`ObjectStore` 根据内容哈希推导对象路径；发布时先 `fdatasync` 临时文件，再用硬链接原子创建正式名称，已存在则复用已有对象。Redis 只缓存 `token_hash → user_id` 及 TTL；缓存失效或不可用时回退 MySQL，因此 Redis 不承载正确性。

## 四条关键运行链路

### 1. 登录与请求鉴权

注册或登录时，`AuthService` 用 Argon2id 校验密码，生成随机会话令牌。浏览器保存原始令牌到 `filelink_session` Cookie，数据库仅保存其 libsodium 通用哈希（BLAKE2b）值。后续请求由 `RequestAuthenticator` 读取 Cookie、计算哈希、优先查询 Redis，再以 MySQL 的未过期会话和用户状态完成最终确认。登出会删除数据库会话并主动删除缓存。

### 2. 分片上传到逻辑文件

上传接口先鉴权并创建属于该用户的 `UploadSession`。客户端按 TUS 偏移量续传；服务端写入分片、维护流式 BLAKE3 哈希，结束后进入 `FINALIZING`，此时取消会返回冲突以避免竞态。完成线程会校验预期哈希，将临时文件发布或复用为 Object；随后在一个 MySQL 事务中锁定/创建 Object、递增引用计数、创建 File，并把会话置为 `COMPLETED`。

因此，“物理对象已存在”不等于“用户已拥有文件”：每次成功上传仍会创建该用户自己的 File；相同内容只复用 Object。

### 3. 私有下载与公开分享

`GET /files`、`GET /files/<id>/download` 和删除接口都按 `owner_user_id` 查询；非所有者得到 `404`，避免泄露文件是否存在。下载通过 Tudou 的文件响应直接发送对象路径，不将大文件整体读入内存。

分享创建接口仅在创建成功时返回一次原始 token；公开下载 `/shares/<token>/download` 会哈希 token，并确认分享未撤销、未过期且关联 File 存在。分享不是 Object 的公开入口，仍是对某个逻辑 File 的限时授权。

### 4. 离线一致性维护

删除 File 时，事务内递减 Object 引用；归零的 Object 标记为 `PENDING_DELETE`。运行 `main` 的离线参数可分别清理过期上传会话、回收待删除 Object，或扫描/回收“磁盘存在但 objects 表没有记录”的孤儿文件。清理与在线请求分开，避免把慢速磁盘扫描塞进 HTTP 请求路径。

## 建议的阅读顺序

1. 先读本文件和 [`src/main.cpp`](../src/main.cpp)，建立“谁创建谁、谁调用谁”的全局图。
2. 阅读 [`database/migrations/202607130001_initial_schema.sql`](../database/migrations/202607130001_initial_schema.sql)，先理解 User → File → Object 与 Share、UploadSession 的关系。
3. 阅读 `src/auth/`，重点区分 Cookie 原始令牌、数据库哈希和 Redis 缓存。
4. 阅读 `src/uploads/UploadService.cpp` 与 `src/storage/ObjectStore.cpp`，理解续传、哈希、原子发布和完成事务。
5. 最后阅读 `src/files/`、`src/shares/`、`src/cleaner/`，将权限、对外 API 与后续回收串起来。

## 一分钟讲述版本

“FileLink 是一个私有云文件服务。我把用户可见的文件和磁盘字节拆成 File/Object 两层：File 表达归属和文件名，Object 用内容哈希唯一标识字节，因此不同用户上传同内容时只复用一份存储。上传采用 TUS 分片续传和流式 BLAKE3 哈希，完成时先原子发布对象，再通过数据库事务创建逻辑文件并维护引用计数。认证使用 HttpOnly Cookie，数据库只存令牌哈希，Redis 只是可失效的会话加速层。删除逻辑文件后异步离线回收零引用对象，分享链接则是对逻辑文件的可撤销、可过期授权。”
