
### 3.3 技术选型：为什么选择命令行参数 (CLI + Cron) 而不是服务内定时器？

针对失效的 `UPLOADING` 临时文件和会话的扫盘清理，我们排除了在 C++ 在线服务进程内部启动常驻定时线程的方案，而是通过命令行参数（`--cleanup-expired`）配合外部 Cron 任务调度。其核心的架构理由如下：

1. **分布式水平扩展友好 (No State Lock Conflict)**：
   若将定时清理内嵌在服务进程中，当服务进行水平扩展（部署多个实例节点）时，所有的节点都会并发对同一个 MySQL 表和同一个共享挂载存储进行过期扫描。这会造成严重的数据库锁冲突，以及“文件已被另一个实例提前 unlink 导致本地抛出 `ENOENT`”的系统调用异常。
   采用独立 CLI 命令，由外部唯一的 Cron 定时单点调起，可以非常轻松地避免多实例争抢冲突。
2. **I/O 与 CPU 物理资源隔离 (Resource Isolation)**：
   清理历史废弃文件（尤其是数十 GB 的大文件）是极其消耗磁盘 I/O 带宽的操作。
   如果在服务内启动定时器，其垃圾清理的执行时机在应用层是不可控的。若在业务高峰期突然执行大量的 `unlink`，会瞬间占满磁盘 I/O 队列，直接挤占正常的 PATCH（上传）和下载写入的吞吐，导致 P99 响应延迟飙升。
   使用外部 CLI 命令，我们可以利用操作系统的进程级调度工具，限制其优先级（例如使用 `ionice -c 3` 限制其只在磁盘空闲时调度），这是在线 C++ 线程做不到的。
3. **极低的冷启动开销 (Lifecycle Efficiency)**：
   当传入 `--cleanup-expired` 启动时，[main.cpp](file:///home/wxm/FileLink/src/main.cpp) 在初始化连接池后直接调用 `SessionCleaner` 并在执行完后立即退出，**完全不装载 HTTP 服务器、UploadService、DownloadService 及其关联的业务逻辑**。这使得该脚本在夜间执行时内存和 CPU 占用极小，执行完后立即释放，对宿主机系统非常友好。
4. **运维可观测性与日志隔离 (Observability & Log Isolation)**：
   离线清理的日志可以直接通过 Cron 标准输出重定向到单独的 `/var/log/filelink_cleanup.log`，避免其高频扫描的垃圾回收日志污染在线 HTTP 服务的核心业务日志，极大降低日常排错的干扰。
