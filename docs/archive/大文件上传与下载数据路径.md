# 大文件上传与下载数据路径

本文记录 FileLink 当前处理大文件时的真实数据路径、内存边界和部署前提。重点不是协议功能列表，而是回答两个问题：文件内容经过哪些进程，以及文件大小是否会直接放大 FileLink 进程内存。

## 结论

| 方向 | 当前方案 | FileLink 进程内存与文件大小的关系 |
| --- | --- | --- |
| 上传 | Tus 顺序分片上传，分片落入 `.part` 文件，最后发布到内容寻址对象存储 | 不缓存整个文件，但 Tudou 会缓存一个完整 PATCH 分片；内存约随“并发分片数 × 单分片大小”增长 |
| 下载 | FileLink 完成授权并返回 `X-Accel-Redirect`，Nginx 从只读对象目录发送文件 | FileLink 不读取文件正文，应用内存不再随下载文件大小增长 |

所以“上传靠分片、下载靠 Nginx `sendfile`”这个理解基本正确，但上传侧必须加上限定：当前并不是 socket 到磁盘的全流式上传，而是以单个分片为内存边界。

## 上传数据路径

当前网页端按 2 MiB 切分文件，然后顺序发送 Tus `PATCH`：

```text
浏览器 File
  │ 每片 2 MiB
  ▼
Nginx
  │ 代理一个 PATCH 请求
  ▼
Tudou HttpRequest::body_（完整保存当前分片）
  │
  ▼
UploadService::write_session_chunk()
  ├─ 校验 owner、Upload-Offset 和剩余长度
  ├─ 写入 storage/uploads/<upload-id>.part
  ├─ fdatasync 当前分片
  ├─ 更新 BLAKE3 流式哈希状态
  └─ MySQL 提交新的 committed_offset
```

### 为什么不会把整个大文件放进应用内存

- 浏览器只发送当前分片，不会把整个文件作为一个 HTTP 请求体上传。
- `UploadService` 收到分片后，将它写到逐步增长的 `.part` 文件。
- BLAKE3 正常路径只保留每个活跃上传的哈希器状态，不保留已经处理过的文件内容。
- 哈希状态丢失时，会使用 64 KiB 缓冲区回读 `.part` 文件重建哈希；仍不会一次读取整个文件。

文件本体主要占用磁盘空间，而不是长期占用 FileLink 堆内存。每个分片执行 `fdatasync()` 后才提交数据库 offset，使返回给客户端的 `Upload-Offset` 对应已经落盘的数据。

### 当前上传并非完全流式

Tudou v1.0.0 的 `HttpContext::on_body()` 会把解析到的字节追加到 `HttpRequest::body_`。只有完整 HTTP 请求解析完成后，Router 才通过 `req.get_body()` 把分片交给 `UploadService`。

因此单个 PATCH 的正文会完整存在于内存中。粗略看，上传正文相关内存上界是：

```text
同时处理的 PATCH 数量 × 单个 PATCH 大小 + 网络/解析过程中的临时副本
```

分片上传避免的是“一个 10 GiB 文件对应一个 10 GiB 请求体”，并不自动阻止客户端故意发送一个超大分片。若未来需要让应用内存与分片大小也解耦，需要 Tudou 提供请求体流式回调或流式 body sink，FileLink 再边接收边写盘。

### 断点续传和最终发布

客户端用 `HEAD /uploads/<id>` 读取服务端已经确认的 `Upload-Offset`，从该位置继续上传。服务端只接受客户端 offset 与数据库 offset 完全相等的分片，避免重试造成重复或错位写入。

最后一个分片完成后：

1. 会话从 `UPLOADING` 进入 `FINALIZING`。
2. 后台线程完成 BLAKE3 校验。
3. `ObjectStore` 使用内容哈希发布或复用 `objects/aa/bb/<hash>`。
4. MySQL 事务创建逻辑 File、增加对象引用并把上传会话标记为 `COMPLETED`。

单个文件的声明大小上限当前为 10 GiB。

## 下载数据路径

私有下载和公开分享下载共用同一条物理发送链路，区别只在授权方式：

```text
客户端
  │ GET /files/<id>/download + Cookie
  │ 或 GET /shares/<token>/download
  ▼
Nginx 反向代理
  ▼
FileLink
  ├─ 校验用户所有权或分享 token
  ├─ 查询逻辑 File 的 content_hash
  ├─ ObjectStore 生成 aa/bb/<hash> 对象键
  └─ 返回 X-Accel-Redirect: /_filelink_objects/aa/bb/<hash>
       响应体为空
  ▼
Nginx 内部重定向
  ├─ internal 阻止客户端直接访问对象地址
  ├─ alias 映射只读挂载的 storage/objects
  └─ 向客户端发送文件
```

FileLink 不再执行 `open/read`，也不再把文件装入 `std::string` 或 Tudou 响应体。它只处理授权、数据库元数据和内部重定向头，所以应用进程的响应内存不会随文件大小线性增长。

当前 Docker 使用的官方 Nginx 镜像在主 `nginx.conf` 中启用了 `sendfile on`。在该部署前提下，Nginx 可以让内核在文件与 socket 之间传输数据，减少用户态复制。这里的准确表述是“避免 FileLink 应用层缓存整个文件并减少用户态复制”，而不是“下载完全不使用内存”：Nginx 缓冲、socket 缓冲和操作系统页缓存仍会使用受控内存。

Nginx 同时原生处理字节范围请求。端到端测试已经覆盖：

- 完整私有文件下载；
- `206 Partial Content` 与 `Content-Range`；
- 客户端直接访问 `/_filelink_objects/...` 返回 404；
- 无 Cookie 的公开分享下载。

## 当前必须注意的配置缺口

### 1. 网页分片大小与 Nginx 请求体限制不一致

网页端当前使用 2 MiB 分片，但项目的 `config/nginx.conf` 没有显式配置 `client_max_body_size`。Nginx 默认限制为 1 MiB，因此按当前代理配置，网页的 2 MiB PATCH 可能在到达 FileLink 前被 Nginx 以 413 拒绝。

部署前必须让以下三个值保持一致：

```text
浏览器 CHUNK_SIZE
    <= Nginx client_max_body_size
    <= FileLink 允许的单分片上限
```

具体值应由并发量和压测决定，而不是只依赖客户端自律。

### 2. FileLink 尚未设置独立的单分片上限

当前服务端只校验“当前分片不能越过文件总长度”，没有独立的 `maxChunkBytes`。如果客户端绕过 Nginx 直连 FileLink，理论上可以发送一个接近剩余文件大小的 PATCH，使 Tudou 在路由前缓存超大请求体。

因此可靠的 OOM 防线必须同时存在于两层：

- Nginx 限制外部请求体大小；
- FileLink/Tudou 在分配或继续接收正文前拒绝超大分片。

### 3. `sendfile` 是部署前提，不是业务代码能力

项目的 server 片段负责 `internal`、`alias` 和反向代理；`sendfile on` 目前来自官方 Nginx 镜像的主配置。若更换镜像或覆盖 `/etc/nginx/nginx.conf`，必须重新确认该指令仍然启用。即使关闭 `sendfile`，下载仍由 Nginx 而不是 FileLink 发送，但用户态复制和资源开销会增加。

## 建议的下一步

最小的后续改动是统一上传分片边界：显式配置 Nginx 的 `client_max_body_size`，并在 FileLink 侧增加相同或更严格的单分片限制及聚焦测试。完成这一步后，才能严格地说“上传内存由受控分片大小约束”。
