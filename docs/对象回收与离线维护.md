# 对象回收与离线维护

在线请求的职责是快速完成用户动作；磁盘扫描、批量删除和崩溃补偿则放到离线任务。FileLink 因此把“文件删除成功”与“物理字节最终被回收”分开：前者立即完成业务语义，后者允许稍后、安全地重试。

这篇文档解释三个独立清理器：过期上传会话、零引用 Object 和磁盘孤儿 Object。

## 为什么不在删除 File 时直接删除磁盘文件

删除逻辑 File 时，系统在一个 MySQL 事务中删除 `files` 记录并把关联 Object 的 `ref_count` 减一。只有减到 0，Object 才进入 `PENDING_DELETE`。

```text
Alice 删除 File(A) ─┐
                    ├─ Object(H) 仍被 Bob 的 File(B) 引用：ref_count 2 → 1，保留字节
Bob 删除 File(B)   ─┘
                      Object(H)：ref_count 1 → 0，标记 PENDING_DELETE
```

若在 HTTP `DELETE` 中立即 `unlink`，会把数据库事务、慢速磁盘 I/O 和失败恢复绑在一次用户请求里：磁盘失败时不知道应否回滚 File；进程中断时也难以判断“字节删了没有”。延后回收后，用户操作只关心 File 是否已删除，后台可以反复尝试物理回收。

## 三类遗留数据

```text
上传中断                         文件删除                    发布后崩溃
    │                               │                            │
    ▼                               ▼                            ▼
UploadSession + .part        ref_count = 0 Object         磁盘 Object，无 DB 行
    │                               │                            │
UploadSessionCleaner         ObjectReclaimer          ObjectOrphanReclaimer
```


| 清理器                  | 处理对象                                    | 启动参数                                                  | 操作是否在线进行 |
| ------------------------- | --------------------------------------------- | ----------------------------------------------------------- | ------------------ |
| `UploadSessionCleaner`  | 过期且仍为`UPLOADING` 的会话及 `.part` 文件 | `--cleanup-expired`                                       | 否，运行后退出   |
| `ObjectReclaimer`       | `ref_count = 0` 的 Object                   | `--reclaim-pending-objects`                               | 否，运行后退出   |
| `ObjectOrphanReclaimer` | 磁盘存在、`objects` 表无记录的正式对象      | `--scan-orphaned-objects` 或 `--reclaim-orphaned-objects` | 否，运行后退出   |

这些参数由 `main.cpp` 读取后直接执行对应任务并退出；未提供参数时进程才启动 HTTP 服务。实际部署可由 cron、systemd timer 或容器定时任务按运维策略调用，而不是让每个用户请求触发全盘扫描。

## 零引用 Object：一套小型回收状态机

`objects.state` 有三个值：

```text
READY ──最后一个 File 删除──► PENDING_DELETE
                                      │
                             回收器原子认领
                                      ▼
                                RECLAIMING
                                  │      │
                           删除成功      非 ENOENT 删除失败
                                  │      │
                       删除磁盘字节和行  └──► 回到 PENDING_DELETE
```

### 1. 从引用计数到待回收

`ObjectDao::remove_reference` 只更新仍有正引用的 Object：

```sql
UPDATE objects
SET state = CASE WHEN ref_count = 1 THEN 'PENDING_DELETE' ELSE state END,
    ref_count = ref_count - 1
WHERE content_hash = :hash AND ref_count > 0
```

所以最后一个 File 删除时，引用数与状态同时改变；引用仍大于 0 时 Object 继续保持 `READY`。

### 2. 用认领避免重复回收

`ObjectReclaimer` 先查询零引用候选，再用条件更新把一个 `PENDING_DELETE` Object 改为 `RECLAIMING`：只有一个并发回收器会更新成功，才可继续删除。

```sql
UPDATE objects SET state = 'RECLAIMING'
WHERE content_hash = :hash
  AND ref_count = 0
  AND state = 'PENDING_DELETE'
```

它随后删除 Object 路径。`unlink` 成功和 `ENOENT` 都被视为“目标字节已不存在”，再删除仍处于 `RECLAIMING` 的数据库行。这样回收器在删除字节后崩溃时，下一次运行仍会看到 `RECLAIMING` 并继续完成收尾；重复 `unlink` 不会伤害正确性。

若 `unlink` 返回其他错误，例如权限或 I/O 错误，回收器将状态退回 `PENDING_DELETE`。下一次离线运行仍可重新认领并尝试。

### 回收与重新引用：拒绝复活已认领对象

回收器把 Object 标记为 `RECLAIMING` 后，`ObjectDao::add_reference` 不会再增加引用数或将状态恢复为 `READY`，而是返回 `Reclaiming`：

```text
回收器：PENDING_DELETE → RECLAIMING
新上传：尝试增加引用 → Reclaiming
上传完成事务：回滚，不创建 File
回收器：可继续 unlink 并删除 Object 记录
```

上传完成流程会将这次会话标记为 `FAILED`，客户端可重新发起上传。它没有尝试“等待回收完成后自动重新发布”这一更复杂的补偿，而是优先保证安全性：绝不生成一个指向可能已被删除字节的 File。

## 过期上传会话：清理临时传输，而不是最终文件

UploadSession 创建后有过期时间。`UploadSessionCleaner` 只选择：

```sql
state = 'UPLOADING' AND expires_at < NOW()
```

它将 `storage/uploads/<upload-id>.part` 删除，然后将会话状态设为 `EXPIRED`。它不会触碰 `FINALIZING` 或 `COMPLETED`：前者可能正在发布 Object，后者已经属于正常文件领域。

这个任务的目标是回收长时间中断的传输空间，而不是删除用户已完成的文件。

### 当前实现边界

清理器对 `ENOENT` 容忍，因此临时文件已被手动删除时仍可把会话安全地标记过期。但如果 `unlink` 返回其他错误，当前实现会打印警告，随后仍将会话标为 `EXPIRED`；该 `.part` 文件不再会被同一查询重新选中。

这意味着 Object 回收器具备显式重试状态，而过期上传清理目前没有针对“物理删除失败”的持久化重试状态。面试中应如实称它为当前的运维边界；若后续增强，可为上传临时文件增加单独的清理失败状态或独立扫描器。

## 孤儿 Object：解决跨系统提交窗口

上传完成必须先把 `.part` 原子发布为正式 Object，再在 MySQL 事务中创建 Object 元数据和 File。这样不会出现“数据库指向不存在的磁盘文件”，但会留下一个反方向的崩溃窗口：

```text
link + 目录 fsync 成功
        │
        ├─ MySQL 事务成功 → 正常 Object + File
        │
        └─ 进程崩溃 / 事务失败 → 磁盘存在对象，objects 表没有该哈希
```

`ObjectOrphanReclaimer` 扫描 `storage/objects/<两位>/<两位>/<64位hash>` 目录结构，只接受路径前缀与文件名一致、名称为小写 64 位十六进制、且确为常规文件的对象。它把文件名还原为二进制哈希，再查询 `objects` 表：无记录即为孤儿。

先运行只读模式确认范围：

```bash
./scripts/run-dev.sh --scan-orphaned-objects
```

确认后再运行删除模式：

```bash
./scripts/run-dev.sh --reclaim-orphaned-objects
```

删除模式会在 `unlink` 前再次查询数据库。若扫描完成后恰好有新事务为该哈希创建了 `objects` 记录，二次检查会跳过该文件，避免把刚变为有效的 Object 删除。

## 一致性策略：优先保守，再最终收敛

这套设计不追求一次操作跨文件系统和 MySQL 的“绝对原子”，因为项目没有分布式事务。它采用更现实的顺序：

1. 在线路径优先避免破坏有效数据：发布字节后才建立数据库引用；删除 File 后才考虑物理删除。
2. 用状态机把可重试的操作显式记录下来：`PENDING_DELETE` 与 `RECLAIMING`。
3. 用离线扫描处理无法被一个事务覆盖的残留：孤儿 Object、过期上传分片。

这叫作**最终一致性与补偿式清理**：短时间内允许无引用字节继续占空间，但最终会被安全回收；回收已认领的 Object 不会被新上传复活，避免误删仍被新 File 引用的内容。

## 面试时的讲述重点

“文件删除时我只在事务内删除逻辑 File 并递减 Object 引用计数；归零对象标记为待回收，而非在用户请求中直接删磁盘。离线回收器通过 `PENDING_DELETE → RECLAIMING` 的条件更新认领对象，删除成功后再删元数据，I/O 失败则退回待回收以便重试。新上传如果发现 Object 已被回收器认领，就拒绝建立 File 并让会话失败重试，避免复活对象后又被物理删除。上传先发布对象后建数据库引用，所以我还实现了孤儿扫描器处理发布成功、事务失败造成的磁盘残留。”
